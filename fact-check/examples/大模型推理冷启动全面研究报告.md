## 1.2 七阶段详细分析

---

### 阶段 1：节点调度与编排

**典型耗时**：1-3 秒（简单 Pod）~ 数分钟（GPU 推理 Pod，含 Gang Scheduling 等待、拓扑约束、多节点编排）  
**瓶颈本质**：Kubernetes 调度器决策延迟 + GPU 拓扑约束 + 多 Pod 协同调度（All-or-Nothing）

> ⚠️ **2026-07 补充**（来源：R9 K8s 调度生态报告）：K8s 社区 v1.35-v1.37 正在密集交付 AI 调度特性，本阶段的分析已从"云平台层"拓展到"K8s 原生调度层"。详见第六部分。

**主流方案**：

| 方案 | 效果 | 复杂度 |
|------|------|--------|
| Karpenter 节点池预热 | 消除 60-120s 扩容延迟 | 中 |
| Provisioned Concurrency（AWS）/ minReplicas ≥ 1 | 消除应用级冷启动 | 低 |
| 分层的节点池（主池常驻 + 爆发池 Spot） | 基线流量零冷启，峰值接受代价 | 中 |
| GCP Vertex AI 并行化部署 | ~1.4 分钟对 ~4.2 分钟（vs SageMaker 串行） | 低（平台侧） |
| **K8s Gang Scheduling（v1.35+）** | 多 GPU Pod 同时就绪，避免部分空转 | 中（K8s 原生） |
| **LeaderWorkerSet 多节点推理（v0.9）** | 多节点模型（DeepSeek-R1 671B）标准化部署 | 中（K8s CRD） |
| **Pod 预创建/复用（Dynamic Containers + WarmPool）** | 绕开调度路径，毫秒级 Pod 绑定 | 中-高（详见 §6.2） |

**核心发现**：

- AWS SageMaker 串行化部署步骤导致冷启动比 GCP Vertex AI 慢 2.5-3.2 倍
- Karpenter + GPU 设备插件存在经典竞态问题：新节点 GPU 设备插件尚未注册但 Pod 已被调度，导致 90-300s 等待（NVIDIA/k8s-device-plugin #291）
- **K8s 新能力**：v1.35 引入的 Gang Scheduling（Workload API）解决了 ML 训练/推理的 All-or-Nothing 需求——传统 Pod-by-Pod 调度可能导致部分 GPU 被"锁定"等待伙伴 Pod
- **LWS** 已被 AWS EKS、GCP GKE、NVIDIA NIM、Red Hat OpenShift 统一采用为多节点推理的部署标准，支持 Gang Scheduling + Exclusive Topology（同组 Pod 独占同一 rack）
- **Dynamic Containers（KEP-5972）** 是 v1.37 最激进的提案：预分配 Pod 后动态增删容器，完全绕开调度路径——适合 Agent sandbox 场景
- **关键结论**：节点调度阶段的优化方向已从单纯的"预置而非按需"扩展到"预创建池 + 快速绑定 + K8s 原生调度特化"的立体方案

### 阶段 2：基础设施就绪

**典型耗时**：60-120 秒（VM 分配 + OS 启动），容器镜像拉取额外 30-60 秒  
**瓶颈本质**：云平台 VM 创建 + 镜像层下载与解压

> ⚠️ **2026-07 补充**（来源：R9）：K8s v1.36 已 GA 多项镜像拉取和 GPU 分配加速特性。

**主流方案**：

| 方案 | 效果 | 来源 |
|------|------|------|
| AWS SageMaker 容器镜像缓存（2026-06） | 镜像拉取从 333s → 0s，端到端 525s → 258s（-51%） | AWS Blog 2026 |
| Custom FUSE 懒加载文件系统（Modal） | 仅加载元数据（几 MB）即可启动，省 300s | Modal Blog 2026 |
| DaemonSet 预拉取镜像 | 省 30-60s | 通用方案 |
| **OCI Image Volumes（K8s v1.36 GA，原 v1.33 beta）** | 模型权重独立分发，镜像从 20GB+ → 几百MB | K8s 上游 |
| EROFS uncompressed vs overlayfs gzip | 镜像拉取 310s vs 344s（不同 snapshotter） | Microsoft 2026 |
| **Lazy Pulling（stargz/Nydus snapshotter）** | 容器启动后按需拉取，无需等全部下载 | containerd 子项目 |
| **DRA Partitionable Devices（v1.36 Beta）** | GPU 动态分区，减少碎片化，小模型更快获得 GPU | K8s 上游 |

**核心发现**：

- 推理容器镜像通常 5-15 GB（vLLM/TensorRT-LLM），镜像拉取占容器冷启动的 44%
- Modal 的自定义 FUSE 文件系统（ImageFS）采用内容寻址多级缓存，将文件系统初始化从 300s 降至 15s
- **Microsoft 2026 实测（Llama 3.1 8B on A100）**：vLLM 的冷启动瓶颈在 startup（权重加载+编译）~176s 而非 pull——去 gzip 对 TTFT 仅改善 1.02x；llama.cpp 瓶颈在 pull——去 gzip 改善 1.35x。**结论：先判断推理引擎再选优化方向**
- **OCI Volume Source（v1.36 GA）**：模型权重不作为镜像层打包，而是独立 OCI artifact 挂载——镜像从 20GB+ 降至几百 MB，镜像拉取从分钟级降到秒级。支持 Lazy Pulling 按需加载
- **DRA Partitionable Devices（v1.36 Beta）**：GPU 动态分区（类似 MIG），减少 GPU 碎片 → 小模型更快挤到空闲 GPU → 减少"等新节点"的延迟
- **关键结论**：容器缓存是本阶段最有效的优化手段。云厂商的容器缓存让镜像拉取变为零成本，K8s 侧的 OCI Volume Source + Lazy Pulling 组合正成为新标准

### 阶段 3：模型获取

**典型耗时**：**60-300 秒**（70B BF16 约 140GB，典型下载带宽 ~1GB/s）  
**瓶颈本质**：远程存储（S3/OSS）的网络吞吐  
**冷启动占比**：占总冷启动的 66%（硬件分析报告 R5），是**最大单一瓶颈**

**主流方案**：

| 方案 | 技术原理 | 效果数据 | 成熟度 |
|------|---------|---------|-------|
| **KServe LocalModelCache CRD** | NVMe 本地预缓存权重，后续 Pod 从本地加载 | 省 60-300s 下载 | ⭐⭐⭐⭐ K8s 生态 |
| **Alluxio 三层缓存**（Inferless） | 热层 NVMe（2.5GB/s+）→ 温层集群共享 → 冷层云存储 | 5GB 模型：冷读 9s，热读 2s（6-12x） | ⭐⭐⭐⭐ 生产 |
| **JuiceFS 分布式文件系统**（BentoML） | POSIX 兼容，按需 chunk 读取 | 20 分钟 → 几分钟 | ⭐⭐⭐⭐ 生产 |
| **PPC/MAIO 可编程 Page Cache**（华为 FAST'26） | I/O 模板追踪 + 精确预取 + BAR 驱逐 | 模型加载降低 **79%**，SSD 带宽利用率 17%→接近峰值 | ⭐⭐⭐ 华为 |
| **百度的守护实例 + RDMA 直传** | 保持实例预设 CUDA 上下文，RDMA 从已有 GPU 拉权重 | Qwen3-235B-A22B（348GB）：~2s | ⭐⭐⭐ 百度云 |
| **Mooncake Transfer Engine** | GPUDirect RDMA 零拷贝 GPU 间传输 | Kimi-K2 1T：53s→7.2s（7x） | ⭐⭐⭐⭐ 千节点生产 |
| **阿里云 PAI 权重服务** | 分布式缓存 + RDMA + 智能分片 | Qwen3-32B：953s→82s（91.4% 减少） | ⭐⭐⭐⭐ 阿里云 |

**核心发现**：

- 模型获取是**冷启动最大瓶颈**（占 60-80%），但也是**最容易被消除的阶段**——只需本地缓存
- 内核 page cache 默认策略下 SSD 带宽利用率仅 **17%**（华为 PPC/MAIO 研究实测）。PPC/MAIO 通过 I/O 模板（DeepSeek-R1-671B 模板仅 545KB）+ BAR（Burn-After-Reading）驱逐，将利用率提升至接近理论峰值
- 百度方案的关键在于：**守护实例**保留 CUDA 上下文（跳过 torch.compile 等阶段），配合 RDMA 权重直传（~2s 传输 348GB），实现接近"秒级"扩缩容
- **关键结论**：本阶段优化的 ROI 最高——本地 NVMe 缓存可完全消除 60-300s 耗时，分布式缓存进一步降低首次下载延迟

### 阶段 4：模型加载到 GPU

**典型耗时**：10-60 秒（含 PCIe 传输 + 反序列化 CPU 开销 + CUDA 上下文初始化 + JIT 编译）  
**瓶颈本质**：PCIe 带宽 + Python 反序列化  
**冷启动占比**：占总冷启动的 7-15%

**主流方案**：

| 方案 | 硬件 | 模型 | 原始 | 优化后 | 加速比 |
|------|------|------|------|--------|--------|
| HuggingFace Safetensors（默认） | A10G + GP3 SSD | Llama3-8B | 48s | — | 基线 |
| NVIDIA Run:ai Model Streamer | A10G + S3（并发 32） | Llama3-8B | 48s | **4.88s** | 10x |
| NVIDIA Run:ai Model Streamer | H100 × 8（TP=8） | Qwen3-235B-A22B（54.92 GiB/GPU） | 320.8s | **47.3s** | 6.8x |
| NVIDIA Run:ai Model Streamer | H100 × 8（TP=8） | Qwen1.5-110B | 80.7s | **25.5s** | 3.2x |
| InstantTensor（SciTix） | H200 × 1 | Qwen3-30B-A3B | 57.4s | **1.77s** | 32.4x |
| InstantTensor（SciTix） | H200 × 8 | DeepSeek-R1 | 160s | **15.3s** | 10.5x |
| CoreWeave Tensorizer | A10G + IO2 SSD（8 workers） | 8B 模型 | — | **10.36s** | — |
| vLLM 分布式加载（PR #3729） | A100 × 8（TP=8） | Llama-2-70B | 249.5s | **141.5s** | -43% |
| 百度 RDMA 直传 | H 系列 | Qwen3-235B-A22B（348GB） | ~10min | **~2s**（权重加载部分） | 300x+ |

**消费级 vs 企业级硬件对比**：

| 维度 | RTX 4090（消费级） | H100 SXM（企业级） | 差距 |
|------|-------------------|-------------------|------|
| 显存 | 24 GB GDDR6X | 80 GB HBM3 | 3.3x |
| 显存带宽 | 1008 GB/s | 3.35 TB/s | 3.32x |

**权重加载时间推算（4090 PCIe Gen4 x16，实测 26 GB/s）**：

- Llama 3.1 8B FP16（16GB）：理论 0.62s，实测 safetensors mmap **2.4s**，无 mmap 的 HF **11s**
- Llama 3.1 70B AWQ INT4（17GB）：理论 0.65s，实测 **3.1s**

**量化对权重加载的影响**：

| 格式 | bits/weight | 相对 FP16 体积 | 加载量减少 | 典型精度损失 |
|------|-------------|---------------|-----------|-------------|
| FP16/BF16 | 16 | 1x | 基线 | 基线 |
| FP8（E4M3） | 8 | 0.5x | 50% | ~1% |
| INT8 | 8 | 0.5x | 50% | <1% |
| INT4/NF4 | 4 | 0.25x | 75% | 2-3% |
| NVFP4（Blackwell） | 4 | 0.25x | 75% | <1%（匹配 BF16） |

**核心发现**：

- 权重加载仅占启动总时间的 **7-10%**（MLSys 2026 vLLM 分析），单独优化权重加载对整体改善仅 **1.04x**
- Model Streamer 通过多线程并发读取 + GPU 直传流水线，在 S3 场景下效果最佳（并发度高）。Azure Blob Storage 实测 Qwen3.5-122B（232.8 GiB）：37.14s vs 默认 225.57s（6.1x）
- InstantTensor 在 H200 + GDS 场景下实现最高加速比（32.4x），但依赖硬件条件
- **关键结论**：量化（INT4/FP4）是最具杠杆效应的手段——直接减少 50-75% 传输字节数，且无需修改框架

### 阶段 5：引擎编译

**典型耗时**：11-70 秒（torch.compile），0.91-60 秒（CUDA Graph 捕获），~60 秒（P2P check）  
**瓶颈本质**：**CPU 密集型编译**（Dynamo 字节码转换 + Triton kernel 编译 + PTX 编译）  
**冷启动占比**：占总冷启动的 55-70%，是**最大耗时阶段**

**详细分解**（vLLM，Llama-70B-FP8，TP=8）：

| 子阶段 | 典型耗时 | 是否 CPU 密集 | 主要依赖 |
|--------|---------|:-----------:|---------|
| P2P access check | ~60s | GPU | GPU 数量（可跳过） |
| torch.compile / Inductor | ~70s | CPU | 层数 × 层复杂度 |
| Dynamo tracing | ~15s | CPU | 字节码量 |
| CUDA graph capture | ~60s | GPU | 模型大小 × batch_size |
| torch.compile（缓存命中） | 3-6s | — | 缓存有效性 |

**主流方案**：

| 方案 | 技术原理 | 效果 | 成熟度 |
|------|---------|------|-------|
| **torch.compile 缓存持久化** | 首次运行后缓存编译图到磁盘 | 11-21s → 3-6s | ⭐⭐⭐⭐⭐ 生产 |
| **CUDA Checkpoint/Restore（cuCheckpointProcess）** | Driver 570+ API，进程级 GPU 状态 dump/restore | **消除**整个编译阶段 | ⭐⭐⭐ Driver 570+ |
| **NVIDIA Dynamo Snapshot（chrek）** | CRIU + cuda-checkpoint + GMS | gpt-oss-120b：105s → <5s（21x） | ⭐⭐⭐ 原型 |
| **thaw** | Rust + CUDA 流水线 DMA，bit-identical 恢复 | Llama-3-70B：546.5s → 31.8s（17.2x）；热交换 0.29s | ⭐⭐⭐ 开源 |
| **Modal 四层架构** | CPU checkpoint（gVisor）+ GPU checkpoint | vLLM 启动：95.7s → 13.8s（6.9x） | ⭐⭐⭐⭐ 生产（15M+ 快照） |
| **百度 Lazy CUDA Graph** | 初始化只捕获最小必要 graph，首请求时完整捕获 | torch.compile + CUDA graph：10-60s → **1-2s** | ⭐⭐⭐ 百度云 |
| **百度一致性哈希缓存** | 扩容场景 100% 命中迁移的编译中间态 | 避免重复 JIT 编译 | ⭐⭐⭐ 百度云 |
| **TensorRT-LLM 引擎缓存** | TRT Network → ONNX → Hash 缓存 | Llama2-70B：重新编译时间降至 40% | ⭐⭐⭐ 生产 |
| **跳过 P2P check** | `VLLM_SKIP_P2P_CHECK=1` | **省 ~60s** | ⭐⭐⭐⭐⭐ 极低复杂性 |

**CUDA Checkpoint/Restore 详解**（NVIDIA Driver 570+）：

| 操作 | 函数 | 说明 |
|------|------|------|
| Lock | `cuCheckpointProcessLock(pid)` | 阻塞新 CUDA 调用，等待 GPU 工作完成 |
| Checkpoint | `cuCheckpointProcessCheckpoint(pid)` | 复制 GPU 内存到主机，释放 GPU 资源 |
| Restore | `cuCheckpointProcessRestore(pid)` | 重新获取 GPU，恢复 CUDA 对象 |
| Unlock | `cuCheckpointProcessUnlock(pid)` | 允许恢复 CUDA 调用 |

保存的状态：设备内存（权重、KV Cache、activations）、CUDA kernels（JIT + torch.compile 产物）、CUDA 对象（streams/contexts/events）、内存映射、CUDA graphs

**注意**：vLLM Sleep Mode 在 v0.14.0 后存在已知 bug（#32714），2026 年 6 月新 issue（#45520）确认在最新 main 分支仍 crash。目前社区 workaround 为 `--disable-v1`。

**核心发现**：

- 引擎编译是**最大耗时阶段**（55-70%），且与模型大小和 CPU 能力强相关
- CUDA checkpoint/restore 是**消除冷启动的终极手段**——通过持久化已编译的 CUDA 上下文，直接跳过 torch.compile + CUDA Graph 捕获
- **关键结论**：仅优化权重加载对整体改善有限（1.04x），**必须**通过 CUDA checkpoint 或编译缓存复用对引擎编译阶段下手，才能实现数量级的冷启动改善

### 阶段 6：运行时初始化

**典型耗时**：0.2-1 秒（KV Cache 分配），0.67-0.97 秒（KV Cache profiling）  
**瓶颈本质**：cudaMalloc 延迟 + block table 初始化

**主流方案**：

| 方案 | 效果 | 复杂度 |
|------|------|--------|
| CUDA Memory Pool 预分配 | 消除 ~200ms cudaMalloc | 低 |
| vLLM APC（Automatic Prefix Caching） | 单实例 10K prompt TTFT 降低 7x | 低（vLLM 原生） |
| SGLang RadixAttention | 相比 vLLM APC 在 RAG 场景 2-6x 吞吐提升 | 低（SGLang 原生） |
| LMCache 多级 KV 缓存（GPU+CPU+NVMe+远程） | 与 vLLM 配合 15x 吞吐提升 | 中 |
| Mooncake Store 分布式 KV 缓存池 | Agentic 负载：1.7%→92.2% 命中率，3.8x 吞吐，46x TTFT 降低 | 高（千节点） |
| vLLM + Mooncake Store 集成 | Round-robin 路由仍保持 >95% 命中率 | 中（PR #40900 已合并） |
| NVIDIA CMX（BlueField-4） | PB 级 KV Cache 持久化，5x tokens/s，5x 能效 | 高（硬件依赖） |

**三种缓存层级性能对比**：

| 层级 | 介质 | 延迟 | 带宽 | 成本/GB |
|------|------|------|------|---------|
| L0 | GPU HBM（H100） | ~0.1 μs | 3 TB/s | 极高 |
| L1 | CPU DRAM | ~80 ns（本地）/ 1-5 μs（GPU 观察） | ~400 GB/s | 高 |
| L2 | NVMe SSD | ~100 μs | ~7 GB/s（Gen5） | 低 |
| L3 | RDMA/远程 | ~5 μs | ~25-50 GB/s（IB NDR） | 中等 |

**KVCache 命中率实际数据**：

| 工作负载 | 方案 | 命中率 | 来源 |
|---------|------|--------|------|
| Agentic 多轮（Codex/SWE-bench） | vLLM baseline（round-robin） | **1.7%** | vLLM Blog 2026-05 |
| Agentic 多轮（Codex/SWE-bench） | vLLM + Mooncake Store | **92.2%** | vLLM Blog 2026-05 |
| Agentic 多轮（合成 30 轮） | vLLM + Mooncake Store（12-60 GPU） | **>95%** | vLLM Blog 2026-05 |
| 通用对话（Kimi 真实负载） | Mooncake（LRU，50K block） | **~51%** | Mooncake FAST'25 |
| llm-d EPP 实测 | KV-aware routing | **87.4%** | Red Hat Blog |
| Mooncake SSD 多轮（8 轮后） | HiCache + Mooncake + SSD | **84%+**（防止断崖） | Mooncake Benchmark |

**缓存感知路由的核心矛盾**：

- **缓存亲和性**（前缀相同路由到同实例 → 高命中率 → 但热点过载）
- **负载均衡**（均匀分布 → 无热点 → 但命中率暴跌至 1.7%）

DualMap（华为/HUST，2026）通过双哈希映射 + Power of Two Choices 首次同时实现两者，提升 2.25x 有效容量。

**核心发现**：

- KVCache 命中率的**天花板由 Workload 特征决定**，而非缓存容量——Mooncake trace 显示 50K block（~2560 万 tokens）后命中率不再增长
- 通用对话场景命中率天花板约 51%，Agentic 负载（131:1 input/output ratio）可达 94%+
- 分布式缓存池（Mooncake Store）是跨实例冷命中的**唯一解**——vLLM baseline round-robin 仅 1.7%，分布式池提升至 92%+
- **关键结论**：KVCache 优化对运行时冷启动影响重大，但需与 Load Balancing 联合设计，否则缓存感知路由失效

---

### 阶段 7：首请求处理

**典型耗时**：0.5s+（短 prompt）到 10s+（长 prompt），取决于前缀是否命中缓存  
**瓶颈本质**：全量 Prefill 计算（无缓存时）

**主流方案**：

- **前缀缓存命中**：TTFT 从 4.3s 降至 0.6s（阿里云 ACK GIE 实测，10K token prompt）
- **KVCache 预热**：Pod 启动后运行 warmup 请求，KServe warmup hooks
- **Mooncake SSD Offload**：防止 DRAM 耗尽后性能断崖——纯 CPU DRAM 方案第 7 轮命中率从 83% 骤降至 36%，增加 SSD offload 后保持 84%+

**核心发现**：

- 首请求冷启动的改善完全依赖前缀缓存命中率，数据预热是关键
- SSD offload 关键价值在于**防止性能断崖**而非追求极致性能

# 第二部分：故障恢复冷启动

大规模 LLM 推理集群的故障率不容忽视——**320 卡集群在任意时刻至少有 18.1% 的节点故障概率**。故障恢复冷启动是独立于常规冷启动的关键维度。

## 2.1 故障率数据

| 来源 | 数据 | 场景 |
|------|------|------|
| Cui et al.（2025） | 单节点 99.5% uptime ≈ 7 分钟 downtime/天 | 大规模 GPU 集群 |
| EEP 论文 | GPU+节点故障占硬件故障 78%，月均 382 次 | 生产数据中心 |
| Tarragon 论文 | 40 节点（320 GPU），任意时刻 ≥1 节点故障概率 18.1% | DeepSeek V3 规模 |
| InfiniteHBD | GPU 相关故障占系统错误 27.05%（最大单一来源） | 大规模 ML 集群 |

## 2.2 恢复策略对比

| 策略 | 恢复时间 | 优点 | 缺点 | 代表系统 |
|------|---------|------|------|---------|
| **全集群重启** | 300-546s | 实现简单 | RTO 极长，不 Scale-Independent | 传统 vLLM |
| **局部 EP 重组（Mutable Membership）** | 11s + 8s 重接入 | Scale-Independent，95% 吞吐 52s 内恢复 | 需运行时支持可变通信域 | **EEP**（SGLang 集成） |
| **Attention/Expert 故障域隔离** | **0.3-0.4s** 停顿 | 故障影响极小 | 需预部署 Shadow Expert | **Tarragon** |
| **无重启恢复** | 秒级 | 完全避免重启 | 依赖 XCCL 和定制通信库 | **ReviveMoE**（华为） |
| **Checkpoint/Restore（thaw/Dynamo）** | 0.29-31.8s | 状态完整恢复，bit-identical | 超大模型 CRIU 瓶颈 | thaw / NVIDIA Dynamo Snapshot |

## 2.3 MoE Expert 级的优雅降级

| 丢失 Expert 比例 | 准确率影响 | 场景 | 来源 |
|-----------------|-----------|------|------|
| Top-8 丢失 1-2 个 | **可忽略** | 生成质量几乎无影响 | ReviveMoE / Not All Experts are Equal |
| Top-8 丢失 25%（2 个） | avg acc drop < 1% | 结构化剪枝 | Not All Experts are Equal（2024） |
| Top-8 丢失 50%（4 个） | 指令遵循下降明显，但可 SFT 恢复 | 分析性研究 | MC-Suite（2025） |

## 2.4 推荐分层容错架构

```
第 1 层：优雅降级（毫秒级）— 丢失 ≤2 Expert → 继续推理，质量损失 <1%
第 2 层：故障域隔离（亚秒级）— Shadow Expert 切换 + KV Cache 异步恢复
第 3 层：可变成员身份重组（秒级）— EEP/ElasticMoE 实时重配置
第 4 层：Checkpoint/Restore（分钟级）— thaw/Dynamo Snapshot 全状态恢复
```

**核心发现**：

- 全集群重启已被学术界和工业界共同否定。核心趋势是**将故障恢复从配置管理问题重新定义为运行时状态有效性问题**
- Tarragon 通过 Attention/Expert 故障域分离实现 0.3-0.4s 停顿，是当前最快速的方案
- thaw 的 0.29s 热交换（55 GB/s，H100 SXM）是当前最快的 C/R 方案

# 第三部分：竞品趋境科技（ATaaS）方案分析

## 3.1 趋境科技的核心主张与事实核查

基于 36 氪报道等公开资料，趋境科技提出 5 个冷启动维度分析。我们对标 6 份研究报告的实际数据：

| 趋境主张 | 研究报告验证 | 结论 |
|---------|------------|------|
| **"7s vs 20min" 冷启动对比** | 百度从 ~10min→~5s（120x+），Modal 2000s→50s（40x），thaw 546.5s→31.8s（17.2x） | **合理范围**。7s 需要 CUDA 上下文持久化 + 权重直传 + 本地缓存三件套 |
| **"KVCache 90% 命中率"** | Agentic workload 下 Mooncake 实测 92-95%，但通用对话只有 51% | **需上下文限定**。仅特定 workload 可达 90%+ |
| **"推理成本降低 10 倍"** | Modal 全栈 ~40x，thaw ~17.2x，Dynamo Snapshot ~21x | **可能合理**，取决于基准定义 |
| **KTransformers：单 24GB 卡驱动 236B** | CPU offload 路线，FlexGen/NEO/CaraServe 均有类似方案 | **技术可行**，但 14 tokens/s 低于生产需求（50+ tokens/s） |

## 3.2 ATaaS 的三大技术支柱

经过对公开资料的技术验证（fact-check 确认 83% 声明）：

### 支柱 1：持久化 CUDA Runtime

- **已验证**：thaw（0.29s 热切换）、vLLM Sleep Mode（1-8s 模型切换）、NVIDIA cuCheckpointProcess API（Driver 570+）
- **关键限制**：跨模型族切换（如 Qwen↔DeepSeek）时 CUDA Graph 和 kernel 缓存不可复用，需重建（增加 1-2s）

### 支柱 2：GPU RDMA Weight Cache

- **已验证**：Mooncake Transfer Engine（Kimi-K2：53s→7.2s）、百度方案（~2s 传输 348GB）
- **关键限制**：消费级 GPU 无 NVLink，PCIe Gen4 仅 26 GB/s，350GB 模型需 35-100s

### 支柱 3：模型族（Model Family）热切换

- **已验证**：同架构模型切换时 CUDA Graph 可完全命中，仅需更新权重
- **关键限制**：跨模型族切换仍需重建 CUDA Graph

## 3.3 7 秒启动的硬件条件

ATaaS 要达到 7 秒启动，必须同时满足：

1. 权重已缓存到远端 GPU HBM（非 SSD）→ RDMA 直传
2. Worker 进程存活（完整 CUDA Runtime 持久化）
3. 模型架构与之前相同或兼容（CUDA Graph 可命中）
4. GPU 支持 cuCheckpoint（Driver 570+，数据中心 GPU）
5. 网络 RDMA 带宽充足（≥200 GB/s 互联）

**任何一条不满足，7 秒启动都会退化到 30s+。**

## 3.4 趋境分析的缺口

| 缺口 | 说明 |
|------|------|
| **未区分不同类型冷启动** | scale-from-zero vs model hot-swap vs 运行时 KV cold miss 需要不同策略 |
| **缺少 CUDA checkpoint/restore 维度** | 这是 2025-2026 年最关键的技术突破 |
| **缺少故障恢复冷启动** | 大规模集群中故障率不可忽视 |
| **缺少 MoE Expert 动态增减** | MoE 占开源模型 60%+，与密集模型有本质差异 |

## 3.5 最接近 ATaaS 承诺的开源组合

```
thaw（GPU snapshot/restore）+ vLLM（inference engine）+ Mooncake Transfer Engine（RDMA 权重直传）
               ↓
  可实现 H100 上 70B 模型 0.3-7s 启动
  消费级 RTX 4090 预计 15-30s（受 PCIe 瓶颈）
```

# 第六部分：Kubernetes 上游 AI 调度与冷启动生态补充

> **来源**：`cold-begin/08-k8s-scheduling-report.md`（2026-07-09）
>
> 以下内容是对主报告"阶段 1：节点调度与编排"和"阶段 3：实例生命周期"的补充——聚焦 K8s 上游社区在 v1.35-v1.37 期间为 LLM 推理和 AI Agent 工作负载推出的调度、编排和冷启动加速特性。

## 6.1 K8s 为何对冷启动至关重要

冷启动的"阶段 1（节点调度）"在 K8s 中涉及：调度器决策、Pod 创建、镜像拉取、GPU 分配、网络就绪。这些步骤串行执行，传统 K8s 对大模型镜像（10-50GB）和 All-or-Nothing GPU 需求支持不足。

**v1.35-v1.37 三个版本密集交付了 AI 调度特性**，核心方向是从 Pod 级调度演进到 Workload 级调度，从静态 GPU 分配演进到动态可分区分配。

## 6.2 对冷启动直接相关的六项 K8s 上游特性

### 特性 1：Pod 预创建与复用（最重要）

K8s 官方正从"按需创建-调度-销毁"向"预创建池 + 快速绑定"模式转变，涉及三个不同层级的方案。

**Dynamic Containers（KEP-5972，目标 v1.37 Alpha）**

最激进的 K8s 上游提案，由 SIG-Node/SIG-Scheduling 联合推进，让 Pod 从"容器集合静态"变成"可动态添加/移除主容器"的执行信封。核心创新是**跳过 Pod 级初始化路径**：容器启动时不经过调度 → sandbox → CNI → volume → init containers 等步骤，因为这些已在 Pod 首次创建时完成。但仍经过 apiserver update、kubelet allocation、CRI start 和镜像拉取。

三个 user story：
- **Agentic Sandbox**：AI Agent 在预分配的 Pod 内按需启动 tool-execution sandbox 容器，隔离性优于 subprocess，但弱于独立 Pod（共享网络 namespace）
- **Shadow Shell**：在目标节点提前调度一个空壳 Pod（资源/网络/volume/init 都准备好），迁移时动态注入 workload container，实现亚秒级恢复。本质是"拿资源换延迟"——预分配资源做 hot standby
- **In-Place Sidecar Upgrade**：启动新版 sidecar，本地蓝绿切换流量，drain 旧版本，无需重建整个 Pod

**SandboxWarmPool（K8s SIG 开源 / GKE GA）**

保持 N 个预热 Pod 在 Pool 中，请求到来时通过 SandboxClaim 直接绑定一个已就绪 Pod，完全绕过调度器。绑定完成后 Pool 自动补充新 Pod。性能：300 Pod/s/集群，90% 在 200ms 内完成。集成 gVisor/Kata Containers 隔离和 Pod Snapshots（空闲 Agent 挂起秒级恢复）。已落地 GKE Agent Sandbox（2026-05 GA，5 个月 16x 增长）。

**GKE Standby Buffer（2026-06 GA）**

节点级方案：预配置 VM 后挂起（仅计磁盘+IP 费，计算成本降至个位数百分比），需要时快速恢复。对比：无 buffer 的集群 P50/P95/P99 延迟卡在 4-6 分钟；有 standby buffer 的集群 P50 降为个位数秒，P95/P99 峰值约 1 分钟即恢复正常。

**对 TokenFactory 的意义**：如果部署在 K8s 上，SandboxWarmPool 模式可将推理 Pod 从调度到就绪的时间从分钟级降到毫秒级，特别适合高频调用的 Agent 场景。Dynamic Containers 更激进（Agent 在热 Pod 内按需启动 sandbox），但依赖 v1.37+。


### 特性 2：LeaderWorkerSet — 多节点推理部署标准

LWS（`leaderworkerset.x-k8s.io`）是 SIG-Apps 孵化的 CRD（v0.9.0，750+ stars），专门解决多主机/多节点 LLM 推理的部署问题。

**核心创新**：
- **Group of Pods as a unit**：一组 Pod（1 Leader + N Worker）作为原子调度单位，并行创建
- **Gang Scheduling**：整组 Pod 全部就绪才调度（All-or-Nothing），避免部分 Pod 占 GPU 空转
- **Exclusive Topology**：可选配置同组 Pod 独占同一 rack，优化跨节点通信带宽
- **Dual Template + StartupPolicy**：Leader 和 Worker 可以用不同模板；可控制是否等 Leader Ready 再创建 Worker
- **DisaggregatedSet API**（设计中）：在 LWS 基础上支持 Prefill/Decode 分离的异构 Pod 组，各自独立扩缩

**生态采用**：AWS EKS（SuperPod 多节点推理）、GCP GKE（DeepSeek-R1 671B/Llama 3.1 405B）、NVIDIA NIM（Multi-Node 推荐方式）、Red Hat OpenShift（OperatorHub）、vLLM、SGLang、llm-d、NVIDIA Dynamo 均已集成。

**对冷启动的影响**：Gang Scheduling 确保多节点推理的所有 Pod 同时就绪，避免逐个调度导致的"部分 Pod 在等 GPU 而先分配到的 GPU 空转"。但不解决单 Pod 内的权重加载/编译延迟。


### 特性 3：DRA Partitionable Devices — GPU 动态分区

KEP-4815，v1.36 Beta，目标 v1.37 GA。这是 DRA（v1.34 GA）生态的重要扩展。

**解决的问题**：传统 Device Plugin 要求静态预分区（如 NVIDIA MIG 需提前用 nvidia-mig-manager 切割），DRA Partitionable Devices 允许**运行时动态分区**——一个物理 GPU 根据工作负载需求实时切分为多个逻辑 GPU，且调度器保证不分配重叠的分区。

```
Physical GPU: H100 80GB
├── Partition A: 40GB → Pod-1 (Llama 7B)
├── Partition B: 20GB → Pod-2 (Embedding)
└── Partition C: 20GB → Pod-3 (Tokenizer)
```

**配套能力**（v1.36 Beta）：
- **Device Taints**：可对故障/保留设备打 taint，仅匹配 toleration 的 Pod 可用
- **Device Binding Conditions**：调度器延迟绑定到外部资源就绪，避免过早分配
- **Resource Health Status**：设备健康信息反映到 Pod status

**对冷启动的影响**：
- GPU 碎片化减少 → 小模型能挤到空闲 GPU 分区 → 减少"等新节点"的冷启动延迟
- 一次完整的 GPU 物理机启动（60-120s）可以分摊给多个推理 Pod
- 对消费级场景：仅支持 NVIDIA MIG（H100/A100）和 AMD/Intel 对应技术，RTX 4090 不支持


### 特性 4：OCI Volume Source — 模型权重独立分发

KEP-4639，v1.36 GA（从 Alpha 到 GA 历时三个版本）。

**核心能力**：将模型权重/配置作为 OCI artifact 卷挂载到 Pod，不再打包进主容器镜像。

```yaml
# v1.36+ Pod 示例
volumes:
  - name: model-weights
    image:
      reference: registry.example.com/models/llama-3.1-8b:latest
```

**对冷启动的影响**：
- 主镜像体积：20GB+（含 CUDA+Torch+CUDA Graph cache+模型权重）→ 几百 MB（纯推理引擎）
- 镜像拉取时间：5-6 分钟 → 数秒
- 权重支持 Lazy Pulling：按需从 registry 拉取 chunk，不要求全部下载完才能启动
- 权重版本管理和 CI/CD 独立于推理引擎

**注意事项**：Lazy Pulling 的效果取决于权重文件的访问模式。Microsoft 2026 实测显示，vLLM 的冷启动瓶颈并非镜像拉取（~166s），而是 startup（~176s，权重加载+JIT 编译）。所以 OCI Volume + Lazy Pulling 主要解决的是**镜像拉取**阶段，对**权重加载到 GPU**阶段无直接影响。


### 特性 5：GAIE Prefix Cache 感知路由

Gateway API Inference Extension 是 SIG-Network 孵化的官方项目（704+ stars），核心组件为 Endpoint Picker（EPP），基于 Envoy ext-proc 协议实现推理感知路由。

**核心能力**：
- **Prefix Cache 感知路由**：EPP 维护每台模型服务器的 Prefix Cache 索引，将共享最长前缀的请求路由到同一服务器，最大化 HBM 缓存命中
- **延迟预测调度**：预测每条请求在各服务器上的 TTFT/TPOT，支持 SLO Header（`x-slo-ttft-ms`），策略可配（least/most/headroom）
- **模型感知路由**：基于 model name 路由，支持 LoRA Adapter 感知、灰度流量分割

**性能数据**（Google Vertex AI 实测，基于 GKE Inference Gateway，底层使用 GAIE/llm-d EPP）：
- Qwen Coder：TTFT 降低 >35% 
- DeepSeek V3：P95 尾延迟改善 52%
- Prefix Cache Hit Rate：从 35% 提升到 **70%**翻倍

**对冷启动的影响**：间接减少冷启动——请求优先路由到缓存命中的热 Pod，减少不必要的新 Pod 创建。与"预创建池"方案是互补关系：WarmPool 解决 Pod 级冷启动，GAIE 减少需要创建新 Pod 的频率。


### 特性 5.5：推理感知路由方案横向对比

GAIE 是 K8s SIG-Network 官方方案，但社区和厂商也推出了多条技术路线。以下针对**Prefix Cache 感知路由**这一核心能力做横向对比。

| 方案 | 项目 | 架构模式 | Prefix Cache 路由算法 | 调度维度 | 多网关节点 | 部署复杂度 | 生态集成 | GitHub |
|------|------|---------|----------------------|---------|-----------|-----------|---------|--------|
| **GAIE** | K8s SIG-Network | Envoy ext-proc + 独立 EPP Pod | Block Hash LRU，最长前缀匹配 | 单网关本地视图 | 需 ext-proc 一致性 | 中等：EPP 以 Sidecar/独立服务部署 | K8s Gateway API 原生 | 704+ |
| **Higress AI** | Alibaba | Envoy Wasm 插件（Go 1.24），**无独立进程** | Redis 分布式 Prefix Tree（SHA-1 block XOR 链），匹配失败用全局最小请求数 | **Redis 全局视图** | 天然多节点共享 | **低**：Wasm 插件热插拔，仅需 Redis | Higress/Envoy+Nacos | 8K+ |
| **llm-d Router** | CNCF Sandbox | 独立 EPP + Envoy ext-proc，复用 GAIE 协议 | 继承 GAIE Prefix Cache 插件 + 延迟预测调度 | 同 GAIE | 同 GAIE | 中：需独立运行 EPP | K8s Gateway API + GAIE InferencePool + 自带 DisaggregatedSet | 244 |

**关键差异分析**：

1. **架构路线差异**
   - **GAIE/llm-d Router/AIBrix**：均基于 Envoy ext-proc 协议，将路由决策外置到独立进程。优点是数据面与控制面分离，策略扩展灵活；缺点是多了一个有状态组件，运维复杂度上升
   - **Higress**：独辟蹊径，将负载均衡逻辑编译为 Wasm 插件直接驻留 Envoy Worker 内。**无独立进程**，部署等同于开一个插件。查询请求基于 Redis 共享前缀树，实现全局视图的同时保持了极简运维
   - **Ray Serve**：框架内建，Prefix Tree 作为 Ray Actor 部署，天然分布式。适合已用 Ray 的团队
   - **Ranvier**：完全自研 C++ 网关，追求极致性能（路由决策 <50μs），但脱离 K8s/Envoy 生态

2. **Prefix Cache 路由实现差异**
   - GAIE/Higress 的核心思路一致：维护每个 Pod 的 KV Cache 索引，请求按最长前缀匹配路由。但 Higress 使用 SHA-1 block XOR 链做前缀树存储在 Redis 中，天然支持多网关节点全局视图
   - GAIE 的 LRU 索引器与 vLLM HBM cache 对齐（需配置 `lruCapacityPerServer` ≈ HBM cache 大小），精度最高但匹配性能受 block hash 碰撞影响
   - Ray Serve 引入多级 fallback：平衡时用前缀匹配，不平衡时用 Power of Two Choices，避免缓存感知路由在负载不均时恶化尾部延迟
   - AIBrix 策略最丰富，含 Preble（Efficient Distributed Prompt Scheduling）和 PD 分离路由

3. **生态成熟度与部署权衡**
   - **Higress**（8K+ stars）是目前社区最活跃的 AI 网关，Wasm 插件设计使其可在任意 Higress/Envoy 上在线热加载，**无需重启或额外部署**。插件提供三种策略（全局最小请求数/前缀匹配/GPU metrics 感知），且已集成到阿里云容器服务 ACS（文档完善）
   - **GAIE**（704 stars）胜在 K8s 官方基因，与 Gateway API、InferencePool、InferenceModel 等 CRD 深度绑定，适合全面拥抱 K8s Gateway API 的团队
   - **llm-d Router** 属 CNCF 沙箱，继承了 GAIE 协议同时扩展了 Prefill/Decode 分离侧边车，适合深度使用 llm-d 推理栈的场景
   - **AIBrix** 策略最全（16+），适合需要精细路由策略调优的大型部署

4. **性能数据对比**

|------|------------------|---------------------|-----------|--------|
| TTFT 改善 | >35% | 50%（240ms→120ms） | 未公开 | 33-44% |
| Cache Hit Rate | 35%→70% | 40%→80%+ | 未公开 | 58-98%
（前缀侧重负载） |

**对 TokenFactory 的启示**：
- **短期最轻量路径**：如果已用 Higress 作为 API 网关，开启 `ai-load-balancer` 插件（prefix_cache 策略）即可获得 Prefix Cache 感知路由，零额外运维成本
- **K8s 原生路径**：如果团队标准化 K8s Gateway API，GAIE 是最合适的选择，但与 Higress Wasm 插件方式相比需要独立维护 EPP 服务
- **重度 Ray 用户**：Ray Serve 内建 PrefixCacheAffinityRouter，框架内零配置
- **极致性能**：Ranvier 的 C++ 自研路线路由开销最低，但脱离主流 Envoy 生态，维护成本高
- **建议**：Higress Wasm 插件方式在部署简便性和全局视图方面优于 GAIE ext-proc 方式，适合不想引入额外有状态组件的团队；GAIE 在 K8s CRD 集成深度上占优

### 特性 6：In-Place Pod Resize — 原地扩缩

v1.35 GA（KEP-1287，6 年从 concept 到 GA）。相比于上述特性的"Pre-create then fast bind"模式，这是另一个减少冷启动的思路：**不创建新 Pod，直接在原地调整资源**。

**关键能力**：
- 容器级 CPU/Memory 原地变更（无需重启，NotRequired 策略）
- Pod 级资源 budget 原地扩缩（v1.36 Beta），适合带 Sidecar 的复杂 Pod
- VPA `InPlaceOrRecreate` 模式（v1.35 Beta）：基于利用率自动扩缩，优先原地变更，必要时重建
- CPU Startup Boost：启动时临时分配更多 CPU 做 JIT 编译/模型加载，完成后自动归还
- KEP-5836（v1.37 讨论中）：Scheduler Preemption for In-Place Pod Resize——当节点资源不足时，调度器抢占低优 Pod 为 Resize 腾空间

**典型场景**：
```yaml
# vLLM 启动时可用 4 CPU 做编译，启动后缩回 1 CPU
spec:
  containers:
  - name: vllm
    resizePolicy:
    - resourceName: cpu
      restartPolicy: NotRequired
```

**对冷启动的影响**：消除了"为冷启动预留额外资源→冷启动结束后浪费"的矛盾。推理服务在启动阶段可临时借用更多 CPU（JIT 编译从 ~70s 降到 ~20s），启动完成后自动释放。Pod 级 Resize 进一步允许 Sidecar（日志代理、指标采集）与主容器共享 Pod 级资源池，减少整体资源预留浪费。

## 6.3 AI Agent 专用调度

K8s 官方目前**没有**专门针对 AI Agent 工作负载的调度特化。Agent 工作负载的特点（不规则到达、多步骤推理链、混合推理+工具调用+状态管理）与现有 K8s 原语之间存在缺口：

- ✅ 已有的：LWS + GAIE 可覆盖 Agent 的推理后端和路由需求
- ❌ 缺失的：Agent 级 SLA/SLO 抽象、Agent 状态感知路由、Agent 专用扩缩策略

不过 GKE 的 Agent Sandbox + SandboxWarmPool 已经为 Agent 提供了"预制池"基础设施，一定程度上弥补了这个缺口。

## 6.4 对 TokenFactory 的战略建议

| 优先级 | 建议 | 理由 |
|--------|------|------|
| 🔴 高 | **LWS 多节点推理编排** + **推理感知路由**（GAIE / Higress / llm-d Router 选型见特性 5.5） | LWS 已成云厂商多节点推理标准编排原语；路由层根据部署条件选 GAIE（K8s 原生）/ Higress（最轻量）/ llm-d Router（深度推理栈） |
| 🔴 高 | **跟踪 DRA Partitionable Devices** v1.37 GA 进展 | GPU 利用率显著提升，直接降低 GPU 碎片化导致的冷启动 |
| 🟡 中 | **采用 OCI Volume Source** 分发模型权重 | v1.36 GA，简化镜像 CI/CD 并加速冷启动 |
| 🟡 中 | **评估 SandboxWarmPool 模式** 用于高频调用场景 | 毫秒级 Pod 分配，对 bursty 推理流量最有效 |
| 🟢 低 | **关注 Dynamic Containers (KEP-5972)** v1.37+ 进展 | 长期可能成为 Agent sandbox 的标准范式 |
