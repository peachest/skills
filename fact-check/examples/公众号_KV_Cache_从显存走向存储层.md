# KV Cache 从显存走向存储层：NVIDIA CMX、SSD-backed KV 和长上下文推理的新架构

**作者**：JW

**原文链接**：https://mp.weixin.qq.com/s/3kIL-pHkffbxNEjfB8wkIw

**摘要**：长上下文和 Agent 推理把 KV Cache 从显存里的临时状态，推成了需要 HBM、DRAM、SSD、DPU 和 RDMA 一起管理的新基础设施问题。存储层不只是扩容量，更会影响 TTFT、GPU stall、p99 延迟和每 token 成本。

---

## 正文

2026 年，NVIDIA 在 Rubin、BlueField-4 和 CMX 里，把一个过去主要藏在推理引擎内部的对象单独拎了出来：KV Cache。这件事和传统 AI 存储不太一样。过去讲 AI 存储，常见对象是训练数据、checkpoint、模型权重、向量库、日志、数据湖。它们都重要，但大多数并不在每个输出 token 的关键路径里。KV Cache 不一样。它由 Prefill 生成，被 Decode 反复读取；上下文长度、并发、会话轮数和 Agent 工作流上来以后，它会一起增长；它可以复用，但复用前提是系统知道它在哪里、值不值得搬、能不能在 GPU 等待前回到正确位置。这就是长上下文推理给基础设施提出的新问题：系统需要更多 KV 容量，但 Decode 又要求 KV 足够近、足够快、足够稳定。存储层能提供容量，也可能把 GPU stall 和 p99 延迟带进推理关键路径。Prefill / Decode、PagedAttention、Prefix Cache、PD 分离和 KV-aware routing，解决的是 serving runtime 怎么管理请求生命周期。这里的问题再往下一层：当 KV Cache 超出 HBM 后，它应该放到哪里？谁负责命名、搬运、预取、驱逐和恢复？为什么 NVIDIA 会把 BlueField、NVMe、Spectrum-X、DOCA、Dynamo 和一批存储厂商拉进同一条链路？这不是“显存不够就丢给 SSD”那么简单。KV Cache 正在把推理系统和存储系统绑到一起。一、KV Cache 为什么会从 HBM 里外溢出来推理系统里有两类很容易混在一起的内存压力。第一类是模型权重。模型权重相对稳定。服务启动时加载，部署周期内长期存在，多个请求共享。它像一个常驻资产，系统要关心的是放不放得下、带宽够不够、量化后精度能不能接受、多卡切分会不会拖慢通信。第二类是 KV Cache。KV Cache 是运行时状态。一个请求读完 prompt 后，模型会为后续逐 token 生成留下 key / value 中间状态。后续每生成一个 token，都要带着这些历史状态继续走。它不是模型长期记忆，也不是应用层把用户文档存起来。它更像推理过程中产生的一串临时账本：请求还活着，它就可能被读取；上下文越长，它越大；并发越高，系统里同时活着的 KV 越多；如果不同请求共享前缀或共享长文档，它又可能跨请求复用。模型权重和 KV Cache 的差别，决定了它们对基础设施的要求不同。模型权重可以提前规划。一个 70B 模型、一个 MoE 模型、一个量化模型，大概需要多少 HBM，部署前就能算出范围。KV Cache 更像流量带来的动态负债。今天用户只是短问短答，HBM 看起来还宽裕；明天业务开始支持 128K 上下文、合同问答、代码库问答、多轮 Agent，KV footprint 就会持续膨胀。长上下文把这个问题放大了。一次长文档问答，不只是输入 token 多一点。系统要先把这段长上下文做 Prefill，生成对应 KV。后面用户继续追问时，如果系统能复用这份 KV，就能少做很多重复 Prefill；如果不能复用，就要反复把同一份材料读进模型。这也是为什么很多长文档场景看起来不像普通聊天。用户以为自己在问同一份文件的不同问题，系统看到的是一批可能高度可复用的上下文状态。如果这份状态只留在某个 GPU worker 的 HBM 里，它的生命周期就很受限制。worker 满了要驱逐，调度换到别的实例要重算，请求跨节点要搬 KV，热门文档可能把少数节点打成热点。所以 HBM 的问题不是简单的“容量不够”。更准确地说，HBM 的机会成本越来越高。同一块 HBM 用来放更多 KV，就不能用来放更大 batch、更多活跃 sequence、更长输出、更高并发冗余。KV 占得越多，scheduler 的自由度越低。系统会更难同时满足 TTFT、ITL、p99 和成本。这时，KV Cache 就开始从一个推理引擎内部对象，变成一个基础设施对象。它要被分层。最热的 KV 放在 HBM，正在 Decode 的请求必须能快读。稍冷但可能复用的 KV 可以去 CPU DRAM。更大、更冷、但仍有复用价值的 KV 可能去本地 NVMe、远端 flash、CXL memory 或专门的 context memory tier。这个层级看起来像传统缓存层级，但它的压力更接近在线推理。因为一次错误的恢复，不只是缓存 miss。它可能让 GPU 等数据，首 token 变慢，输出流抖动，p99 突然炸掉。二、把 KV 放到 SSD，为什么不是普通缓存问题SSD 很容易让人产生一个直觉：HBM 贵，SSD 便宜。KV 太大，就放 SSD。这个直觉只说对了一小半。SSD 的确提供容量。问题在于，大模型推理不是离线归档系统。KV Cache 不是一批可以慢慢读回来的冷文件。它有明确的 tensor layout，有 layer、head、block、sequence position、dtype；它可能被分成很多 block；它和推理引擎内部的 block table、scheduler、prefix cache、KV connector 绑定在一起。更麻烦的是，KV 的恢复时机直接影响用户体感。如果一个请求需要复用某段长上下文，系统必须在 Decode 需要这些 KV 之前把它们放回足够近的位置。太晚回来，GPU 等；回来不全，还是要重算；恢复路径抖动，p99 就会变差。所以 KV Offload 的目标不是“能存下”。KV Offload 的目标是：在 Decode 需要之前，把正确的 KV 放回正确的位置。这件事比普通缓存难。普通 Web 缓存里，一个对象 miss 了，可能去数据库读一次，慢几百毫秒，但请求通常还是完整执行。推理系统里，KV restore 如果落在首 token 路径上，TTFT 会直接变差；如果落在输出中途，用户会看到流式输出卡住；如果大量请求同时 restore，GPU 利用率可能看起来不满，但根因不是算力不够，而是数据没回来。2026 年 5 月发布的 Tutti 论文，抓的就是这个问题。论文的背景很直接：长上下文把 KV Cache footprint 推到 GPU HBM 甚至 CPU DRAM 之外，系统开始把 KV offload 到 NVMe SSD。但从 SSD 恢复 KV 时，I/O 性能不好，GPU 会 stall。为什么 NVMe 理论带宽很高，到了 KV restore 这里还会卡？论文指出一个关键原因：GPU memory layout 是碎片化的，KV restore 可能变成大量 tiny random I/O。即使用 GPU Direct Storage，CPU 仍可能参与 I/O 发起和控制，变成低并行度瓶颈。也就是说，问题不是“SSD 慢”这么粗。问题是 KV 的布局、I/O 粒度、CPU 控制路径和 GPU 等待，被串在了同一条关键路径上。一个系统如果只是把 KV block 写成文件，再等需要时读回来，可能会遇到几类问题：·I/O 太碎，NVMe 带宽吃不满。·CPU 要管理大量 I/O 请求，成为控制路径瓶颈。·restore 时机不准，GPU 等 KV。·offload 策略只看容量，不看未来 Decode 何时需要。·eviction 和 prefetch 不协调，热 KV 被提前赶走。所以 SSD-backed KV 的工程价值，不取决于能不能把 KV 写到盘上。它取决于恢复路径能不能稳定。Tutti 的方案是把路径往 GPU 侧推：GPU-centric KV cache object store、GPU io_uring、slack-aware I/O scheduling。它想减少 CPU 在关键数据和 I/O 控制路径里的参与，把碎片化 KV 管理成更适合批量搬运的对象，并在 GPU 有空隙时安排 I/O，减少对计算路径的干扰。论文给出的结果很激进：相比 GDS-enabled SSD-backed LMCache，在严格 SLO 下 TTFT 降低 78.3%，可承载请求率提升 2x，serving cost 降低 27%。这里要注意口径。这是论文评测结果，不等于所有生产系统都能直接拿到同样收益。模型、上下文长度、SSD、GPU、runtime、SLO、workload mix 都会改变结果。但它说明一件事：SSD-backed KV 要优化的不是存储容量，而是 GPU 不要为了等 KV 恢复而停下来。这也解释了为什么 KV Cache 一旦走向存储层，就不能只交给传统存储团队。推理 runtime、GPU I/O、网络、cache metadata、scheduler 都要进入同一个设计空间。三、NVIDIA CMX 想把 KV 做成 pod-level context tierNVIDIA CMX 的信号很明显。官方把它叫 context memory storage，不是普通 AI storage。NVIDIA 的 CMX 页面把它定位为 long-context、multi-turn、agentic AI inference 的 AI-native context tier。它由 BlueField-4 storage processor 驱动，用来扩展 GPU memory，提供 pod-level context tier，优化 ephemeral KV cache。这几个词放在一起，说明它瞄准的不是训练数据湖，也不是普通模型仓库。它瞄准的是推理过程里的上下文状态。NVIDIA 技术博客把这个层级说成 Rubin platform 里的 G3.5 context memory tier：一个基于 flash、面向 latency-sensitive KV cache 的 pod-level 架构。官方宣称，相比 traditional storage，这套方案可带来最高 5x tokens-per-second 和 5x power efficiency。这些性能数字要按官方口径看，不应该直接写成行业已验证结论。更值得看的，是它的系统组成。CMX 不是简单给 GPU pod 接一堆 SSD。BlueField-4 负责管理 NVMe SSD，运行存储服务，并为 KV cache offload data integrity 和 encryption。DOCA Memos 提供面向 BlueField-4 和 CMX 优化的 SDK，暴露 key-value API，把 Ethernet-attached flash 变成 pod-level cache tier。Spectrum-X Ethernet 提供 RDMA fabric，目标是低延迟、高带宽、低抖动访问共享 KV。这套组合说明，NVIDIA 想解决的不是“哪里有容量”。它想把 KV 的数据面做成 GPU pod 的一部分。为什么需要 DPU？因为如果 KV restore 和共享路径大量经过 host CPU，CPU 就会变成控制面和数据面瓶颈。长上下文和 Agent 工作流会制造大量上下文状态，GPU 等待这些状态时，昂贵的计算资源可能被 I/O 抖动拖住。BlueField 的位置，正好在计算、网络和存储之间。它可以管理 NVMe，可以处理网络，可以做安全和完整性，也可以通过 DOCA 暴露更贴近应用的数据接口。对于 KV Cache 这种既要容量、又要低延迟、还要隔离和安全的运行时状态，这个位置比普通 CPU + 存储阵列更接近问题中心。为什么需要 Spectrum-X？因为一旦 KV 不是本地 worker 私有状态，而是 pod-level 共享资源，网络就进入关键路径。传统存储网络如果 tail latency 抖得厉害，推理系统会很难控制 p99。对长上下文推理来说，平均带宽好看不够，restore 的尾部延迟也要可控。为什么需要 DOCA Memos 这种 KV API？因为推理系统不只需要读写文件。它需要按 KV block、context、tenant、模型、生命周期、TTL、ownership 来管理状态。应用最好不要自己维护复杂的盘路径和传输细节，而是通过一个更贴近 KV 语义的接口，把命名、路由、完整性、安全和复用交给 context tier。所以 CMX 的重点不是“NVIDIA 要卖存储”。更准确地说：GPU pod 需要一个比普通存储更靠近推理路径的 context memory tier。这个 tier 不会替代 HBM。正在 Decode 的热 KV 仍然需要在 HBM 或足够近的位置。CMX 更像一个大容量、共享、可预取、可复用的上下文层，用来承接那些不该一直占 HBM、但也不能像冷数据一样慢慢读的 KV。它填的是 HBM 和传统存储之间的空档。这个空档过去不明显，是因为上下文短、Agent 少、KV 复用价值不够高。长上下文和多轮 Agent 把这个空档撑大了。四、Tutti 说明 SSD-backed KV 的难点在 I/O 控制路径CMX 是厂商从系统产品侧给出的答案。Tutti 则从操作系统和 GPU I/O 路径上解释，为什么 SSD-backed KV 需要重新设计。它抓住了一个很具体的矛盾：NVMe SSD 有容量，也有不错的顺序带宽，但 KV restore 不是理想顺序读。KV Cache 在推理引擎里通常被 block 化管理。为了减少 HBM 碎片、支持 prefix reuse、支持不同 sequence 动态增长，系统会让 KV 在物理内存里呈现非连续布局。等这些 KV 被 offload 到 SSD，再需要恢复时，访问模式可能变得非常碎。碎 I/O 会带来两个后果。第一，存储设备理论带宽很难吃满。第二，I/O 请求管理本身会消耗控制路径资源。如果 CPU 负责发起和管理这些 I/O，CPU 可能成为瓶颈。即使数据能通过 GDS 走得更直接，I/O 控制仍可能是 CPU-centric。GPU 端看见的结果就是：数据没及时回来，计算等着。Tutti 的第一步，是做 GPU-native object abstraction。这不是为了发明新名词，而是为了把 KV 从“很多碎块”重新组织成 GPU 更容易管理和搬运的对象。对象化之后，系统可以做更大粒度、更高并行度的传输，减少 tiny random I/O 对路径的破坏。第二步，是 GPU io_uring。Linux io_uring 的思路是用提交队列和完成队列降低异步 I/O 开销。Tutti 把类似思想放到 GPU 侧，让 GPU 更直接地发起和管理对象 I/O，减少 CPU 参与关键控制路径。第三步，是 slack-aware I/O scheduling。推理不是一直同样忙。GPU 上有计算任务，也有可以插入 I/O 的窗口。I/O 如果安排错了，会和计算争资源；安排太晚，Decode 要用时还没回来。slack-aware 的目标，是在不破坏关键计算路径的前提下，把 KV 及时恢复回来。这三个点合起来，Tutti 不是简单说“SSD 可以当 KV 扩展”。它说的是：如果要让 SSD-backed KV 在长上下文 serving 里实用，必须重新设计 KV 对象、I/O 发起方式和调度时机。这对生产系统有一个很重要的提醒。当团队评估 KV offload 时，不应该只问：·SSD 多大？·NVMe 带宽多少？·是否支持 GDS？还要问：·KV block 在 HBM 和 SSD 里是什么布局？·restore 是小 I/O 还是批量对象传输？·CPU 是否还在关键控制路径上？·prefetch 是否知道 Decode 什么时候会用？·I/O 是否会抢 GPU 计算资源？·p99 是不是被少量 restore 慢路径拉坏？这些问题都不是传统容量规划能回答的。它们属于推理 runtime、存储路径和 GPU 调度的交叉地带。还有一个更新也指向同一件事。2026 年 5 月 13 日提交的 KVServe 论文，把 disaggregated serving 里的 KV 明确描述成跨网络和存储边界移动的 payload。它讨论的不是把 KV 放到哪一层，而是当 KV 需要跨节点传输时，压缩策略不能只做静态配置，还要根据 workload mix、带宽、SLO 和质量预算动态选择。这说明 KV 问题正在继续往外扩展。第一阶段是 HBM 放不下，要不要 offload。第二阶段是 offload 后怎么 restore，避免 GPU stall。第三阶段是 KV 变成跨节点 payload 后，网络、压缩、质量和 SLO 也要一起进入调度。五、Mooncake、LMCache、Dynamo：runtime 开始同时调度 compute 和 stateKV Cache 走向存储层，还有另一条线：serving runtime 本身在变化。Mooncake 是一个很好的例子。Mooncake 的论文标题就叫 KVCache-centric disaggregated architecture。它服务的是 Kimi 这类长上下文 LLM 服务，主要做法包括分离 prefill 和 decoding clusters，利用 GPU 集群中未充分使用的 CPU、DRAM、SSD 组成 disaggregated cache，并用 KVCache-centric scheduler 在吞吐和 latency SLO 之间做取舍。论文里还有一个具体机制：early rejection。传统 serving 研究常默认请求都会被处理。Mooncake 面对的是过载场景：请求太多时，系统不一定应该把所有请求都拖进队列。因为一旦请求进入系统，它不仅占计算，还可能占 KV、占缓存、占未来的 Decode slot。这和 KV storage tier 的逻辑是一致的。系统不再只是调度 compute。它还要调度 state。一个请求进入系统后，产生的不是一次无状态计算，而是一段可能长期占用资源的 KV 状态。这个状态在哪里、能不能复用、什么时候驱逐、要不要提前拒绝请求，都会影响整体 SLO。2026 年 5 月，vLLM 也把 Mooncake Store 集成进了分布式 KV cache pool。它给出的 agentic workload 例子很直观：多轮 Agent 会反复携带大量共享前缀，下一轮只新增一小段工具结果或用户输入。如果请求被路由到另一个实例，本地 prefix cache 就会 miss，系统不得不重算。分布式 KV cache pool 的目标，就是让这些跨轮次、跨实例的 KV 不再困在单个 vLLM worker 里。这条更新说明，KV storage tier 不只是论文里的 long-document QA 优化，也开始进入真实 Agent serving stack 的工程路线。Agent 工作负载会把“共享前缀很大、新增 delta 很小、请求跨实例移动”这三个条件同时摆到系统面前。LMCache 则从另一个角度说明 KV 层正在独立出来。它的目标是让可复用文本的 KV 能跨 serving engine instance 复用。LMCache 文档里的 local disk backend 默认关闭，不像 CPU RAM offload 那样预设一块空间。启用 disk backend 后，它会按 KV cache chunk 创建文件，容量超限时用 LRU 驱逐。disk 和 remote backend 支持 async put，local disk 支持 prefetch 到 CPU RAM。这些细节说明，KV offload 不是“打开一个开关就完事”。它需要 chunk size、backend、容量、异步写入、预取、驱逐策略一起配合。文档里通过 vLLM 的 --kv-transfer-config 接入 LMCache connector，也说明现代推理引擎已经开始把 KV transfer 和外部 KV layer 当作可插拔路径。NVIDIA Dynamo KVBM 也是同一类演进。KVBM，也就是 KV Block Manager，被定义为处理 KV block allocation、management、remote sharing 的 runtime component。它面向异构和分布式环境，可以作为 vLLM、TensorRT-LLM 等框架的统一内存层和 write-through cache。这里的关键词不是某一个框架名，而是一组运行时对象：block allocation、layout、remote sharing、storage backend、metrics、events。这些过去很容易被看成推理引擎内部实现细节。现在它们被抬到独立组件层。原因很简单：当 KV 只能待在本地 HBM 里，engine 自己管就够了。当 KV 可以去 CPU、去 disk、去远端、跨实例复用、跨节点传输，engine 内部的一套 block table 就不够了。系统需要一个更明确的 KV 管理层，处理 layout、位置、生命周期、事件和指标。vLLM 的 Automatic Prefix Caching 也可以放在这里理解。APC 缓存已有请求的 KV cache，当新请求共享前缀时，可以跳过共享部分的 Prefill。它对长文档反复提问、多轮会话很有价值。但 vLLM 文档也明确了边界：APC 主要减少 Prefill，不减少 Decode；如果请求没有共享前缀，收益就不明显；如果生成答案很长，系统大部分时间花在 Decode，APC 带来的收益也会被稀释。这说明 KV reuse 的价值强依赖 workload。它不是一个普适加速按钮。把 Mooncake、LMCache、Dynamo、vLLM APC 放在一起看，主线就很清楚：KV Cache 正在从 inference engine 的内部状态，变成跨实例、跨层级、跨介质管理的资源。一旦它变成资源，serving runtime 就必须同时调度 compute 和 state。调度 compute，问的是哪张 GPU、哪个 batch、哪个 worker。调度 state，还要问：·KV 在哪里？·谁拥有它？·是否还新鲜？·是否可被这个租户访问？·搬回来要多久？·命中一次能省多少 Prefill？·为了命中多排队是否划算？·驱逐它会不会让后续请求重算？这就是为什么 KV storage tier 不能脱离 runtime 讨论。一个只懂容量的存储层，不知道哪个 KV 未来会热。一个只懂本地 batch 的推理引擎，不知道远端 KV 什么时候能回来。中间必须有一层共同语言。六、CXL 和远端内存：比 SSD 更近，但也不是免费SSD 不是唯一方向。如果说 SSD-backed KV 解决的是容量问题，那么 CXL 和远端内存更像是在问：能不能给 GPU 集群一个更像内存扩展的 KV 层？CXL 的吸引力在于，它可以让系统把远端或扩展内存以更接近 memory semantics 的方式纳入架构。对 KV Cache 这种不完全适合块存储、又放不下全热 HBM 的状态来说，这个方向很自然。CXL-SpecKV 这类研究方案，就是沿着这个方向走。它提出用 CXL-based memory disaggregation，把 KV cache offload 到远端 FPGA memory；再配合 speculative KV-cache prefetching 和 FPGA 加速的 KV compression / decompression，降低 GPU 端内存压力和带宽压力。论文声称，在评测中能达到最高 3.2x 吞吐提升和 2.8x 内存成本降低。同样，这要按研究方案理解，不应该写成已经成熟落地的通用工程结论。但方向值得看。SSD-backed KV 的弱点，是块设备路径和恢复延迟。CXL / disaggregated memory 想提供更近的容量层。它可能比 SSD 更适合某些需要低延迟恢复的 KV，但它也不是免费午餐。它会带来新的问题：·CXL 拓扑怎么设计？·多 GPU 如何共享远端内存？·带宽争用如何隔离？·远端内存故障如何恢复？·压缩和解压是否进入关键路径？·speculative prefetch 猜错会浪费多少带宽？·软件栈成熟度能否支撑生产运维？也就是说，CXL 的方向并不推翻前面的判断。它只是说明 KV storage tier 不一定只有 SSD。问题变成了：在容量、延迟、成本和可调度性之间，KV 应该处在哪一层。HBM 近，但贵。CPU DRAM 容量更大，但离 GPU 更远。NVMe 容量更便宜，但恢复路径容易抖。远端 flash / CMX 可以做 pod-level 共享，但依赖 DPU、RDMA、metadata 和 runtime 协同。CXL memory 更像内存扩展，但要面对拓扑、成本和生态成熟度。这些层级没有谁能单独赢。它们更像一组缓存层。区别在于，传统缓存层面对的是应用对象；KV 层面对的是 token 生成路径里的运行时状态。七、什么时候该上 KV 存储层，什么时候不值得不是所有推理服务都需要 CMX、SSD-backed KV 或 CXL KV。有些场景上了只会增加复杂度。判断要从 workload 开始。第一，看上下文有多长。短问短答客服、简单分类、短文本改写，KV footprint 很有限。哪怕有 prefix cache，复用收益也不一定能覆盖外部 KV 层的复杂度。长文档问答、代码库问答、合同审查、企业知识库、多轮 Agent，更容易产生大 KV 和重复上下文。这类场景才有更强动机把 KV 从 HBM 外溢出去。第二，看复用是否稳定。同一份文档被多人反复问，同一套工具 schema 被所有 Agent 请求复用，同一段系统提示词长期稳定，这些都适合缓存。如果每个请求都完全不同，prefix 不稳定，检索结果高度变化，KV 存储层的命中率就可能不好看。第三，看延迟目标。如果业务允许较高 TTFT，或者主要跑离线批处理，KV restore 慢一点也许可以接受。如果是交互式聊天、代码补全、语音助手，restore 进入关键路径就很危险。第四，看输出长度。APC 和很多 KV reuse 主要省 Prefill。如果请求主要时间花在长 Decode，比如长篇创作、长报告生成，Prefill 复用的收益会被 Decode 时间稀释。此时系统更要关注 ITL、Decode batch、HBM bandwidth，而不是只盯 KV storage tier。第五，看网络和运维能力。远端 KV 层一旦进入路径，RDMA tail latency、metadata freshness、eviction policy、tenant isolation、monitoring 都要跟上。团队如果还没有成熟的 observability 和故障处理，贸然引入远端 KV，可能只是把问题从 HBM 压力转移到分布式系统里。可以用一个简单矩阵判断：场景KV storage tier 价值主要风险长文档反复问答高restore 路径拉高 TTFT多轮 Agent 固定工具 schema中到高热点 prefix 造成局部拥塞短问短答客服低系统复杂度大于收益长输出创作中低Decode 时间占主导，Prefill 复用收益有限高并发企业 RAG高metadata、租户隔离、cache policy离线批处理视情况吞吐优先，不一定需要低延迟 context tier 这里的判断是：KV storage tier 的价值来自“可复用长上下文 + 可预测恢复路径”，不是来自“SSD 比 HBM 便宜”。如果长上下文不可复用，存储层只是把临时状态搬远。如果恢复路径不可预测，存储层会把 p99 风险带回来。如果 runtime 不知道 KV 在哪里，cache hit 也可能变成局部热点。如果业务没有强 SLO，复杂架构可能不值得。八、存储进入关键路径以后，系统会怎么坏KV 进入存储层以后，故障模式会变。以前推理慢，团队可能先看 GPU utilization、batch size、queue depth、模型 kernel、显存水位。以后还要看 cache metadata、storage queue、RDMA tail latency、restore latency、prefetch miss、eviction conflict。第一类故障是 metadata stale。Router 或 scheduler 以为某段 KV 还在某个节点或某个 context tier，实际已经被驱逐。请求被路由过去以后，发现 miss，只能重算或从更慢层恢复。这个路径会让 TTFT 难以预测。第二类故障是 prefetch miss。系统知道未来可能要用某段 KV，但预取太晚、预测错误或 I/O 被其他请求占住。Decode 要用时，KV 还没回来，GPU 等。第三类故障是 remote hotspot。热门文档、热门 system prompt、热门工具 schema 会吸引大量请求访问同一批 KV。如果 routing 只看 cache hit，不看队列和网络拥塞，就会把请求推向少数节点或少数 context tier，最后 cache hit rate 很高，p99 也很高。第四类故障是 eviction conflict。推理 runtime 认为某段 KV 未来还有价值，但 storage layer 的 LRU 或容量策略刚好把它赶走。下次请求来了，系统以为会命中，最后重算。第五类故障是 noisy neighbor。多租户共享 context tier 时，一个租户的长上下文 workload 可能占用大量 KV 容量和 restore 带宽，影响其他租户的交互延迟。第六类故障是安全和隔离。KV Cache 是模型中间状态，里面虽然不是原始文本，但和租户上下文高度相关。它能不能跨请求复用、跨租户隔离、如何加密、如何设置 TTL、是否进入审计范围，都需要明确边界。第七类故障是 observability gap。GPU 利用率低，不一定是没流量。可能是 GPU 在等远端 KV。TTFT 高，不一定是 Prefill 算得慢。可能是 restore 慢、metadata 过期、prefix hit 误判。p99 高，不一定是模型 kernel 抖。可能是 RDMA tail latency、SSD GC、context tier 热点或 eviction policy 打架。所以 KV storage tier 上线后，指标体系也要变。至少要能看到：·KV hit rate / miss rate。·local hit / remote hit / disk hit。·restore latency p50 / p95 / p99。·prefetch success rate。·eviction reason。·metadata stale rate。·GPU stall attributable to KV restore。·per-tenant KV footprint。·RDMA tail latency。·storage queue depth。没有这些指标，团队很容易误判。看起来是 GPU 不够，其实是 KV 没回来。看起来是 cache 命中率不错，其实命中路径太远。看起来是 SSD 带宽够，其实小 I/O 和 CPU 控制路径把 GPU 卡住。九、以后看 AI 存储，要问它离 token 有多近KV Cache 从显存走向存储层，不代表 HBM 不重要。恰好相反，它说明 HBM 更重要了。最热的 KV 仍然必须靠近 Decode。HBM 负责正在生成的 token 状态，承担最低延迟和最高带宽的路径。外部 KV 层的价值，是把不该长期占 HBM、但未来可能复用的上下文状态移出去，并在需要前尽量拿回来。这不是替代关系。这是分层关系。以后判断一个 AI 存储产品，不能只问容量多大、带宽多高、每 TB 多少钱。要先问它服务的对象是什么。如果服务的是训练数据，它关心的是吞吐、并发读取、数据准备、checkpoint 周期。如果服务的是模型权重，它关心的是加载时间、分发、版本、冷启动。如果服务的是向量库和 RAG 文档，它关心的是检索、更新、权限、召回和排序。如果服务的是 KV Cache，问题就完全不同：1. 这段 KV 是 per-request 私有，还是跨请求复用？2. 命中一次能省多少 Prefill？3. restore 一次会增加多少 TTFT？4. 它是否可能影响 Decode 中途的 ITL？5. 数据路径是否绕 CPU？6. 网络 tail latency 是否可控？7. cache metadata 是否足够新？8. eviction、prefetch、routing、scheduler 是否协同？9. 租户隔离和加密在哪里做？10. 如果关掉这层，系统损失的是容量、成本、吞吐，还是用户体感？这些问题决定了 KV storage tier 是基础设施升级，还是复杂度陷阱。NVIDIA CMX、Tutti、Mooncake、LMCache、Dynamo KVBM、CXL-SpecKV 指向的不是同一个产品形态，但它们都在回答同一个系统问题：当长上下文和 Agent 把 KV Cache 放大到 HBM 之外，推理系统要怎么继续保持低延迟、低成本和高吞吐？答案不会是一层存储解决所有问题。更可能是一条更细的运行时数据面：HBM 承接最热的 token 状态。DRAM、SSD、CXL、context memory tier 承接可复用上下文。DPU 和 RDMA 尽量把恢复路径从 CPU 和慢网络里解放出来。serving runtime 决定哪些 KV 值得留、值得搬、值得预取、值得驱逐。所以 KV Cache 从显存走向存储层，改变的是基础设施分工。GPU 不再只是吃模型权重和矩阵计算。存储也不再只是放训练数据和 checkpoint。中间出现了一种新的热状态：生命周期短，容量大，延迟敏感，可复用，但非常依赖位置。谁能把这类状态管理好，谁就能在长上下文、多轮 Agent 和高并发推理里少浪费 GPU。以后看 AI 存储，不妨先问一个问题：它在一个 token 生成之前，能不能把正确的 KV 放回正确的位置？参考资料·NVIDIA CMX Context Memory Storage
