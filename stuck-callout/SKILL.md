# Stuck Callout

当你（agent）在解决一个复杂任务时反复尝试却无法推进，或者人类用户主动询问你的状态时，生成一份*阻塞报告*。这份报告的目标是让人类**不需要翻阅前面的对话历史**，就能快速理解你遇到了什么阻碍。

## 何时触发

两种模式下触发：

1. **用户手动触发** — 用户说"卡住了" / "stuck" / "你卡住了" / "出了什么问题" / "你在干什么" / "什么情况" 等，直接执行。
2. **Agent 自检触发** — 当你发现以下信号时，主动发起 callout：
   - 同一函数/文件/工具被反复调用 3+ 次但无明显进展
   - 尝试了 2+ 种不同方法但都失败了
   - 连续收到非预期的错误或异常
   - 输出结果明显不正确但无法定位根因
   - 某个步骤阻塞了 5+ 轮交互

## 输出模板

ALWAYS 使用以下结构化模板输出（渲染为 Markdown）：

```
## ⛔ 阻塞报告：<一句话概括当前阻碍>

### 1. 目标
<原任务的一句话描述>

### 2. 尝试过的方法

| # | 方法 | 结果 |
|---|------|------|
| 1 | <做了什么> | <失败了/部分成功/不确定> |
| 2 | <做了什么> | <失败了/部分成功/不确定> |

### 3. 当前假设
- <我认为的原因 1>
- <我认为的原因 2>

### 4. 卡住的根因
<直击核心的一句话。如果是用户手动触发的，说明此前的推理路径中哪一步走错了>

### 5. 需要人类帮助
- [ ] <具体需要人类确认/决定/提供的信息 1>
- [ ] <具体需要人类确认/决定/提供的信息 2>

### 6. 尝试继续的话，下一步会做什么
<如果人类不介入，计划的下一个尝试>
```

## 执行流程

### Step 1 — 收集上下文

回顾当前会话中的关键信息：

- 原始任务描述
- 已经尝试过的方法（列出每个方法的核心思路和结果）
- 当前对问题的理解/假设
- 如果需要，查看最近的调试输出、错误信息、文件内容来确认状态

Do not proceed until you have concrete items for each section.

### Step 2 — 填充模板

按照上述模板填写。注意：

- **尝试过的方法**只填关键尝试，不要列出所有细微的调试步骤。3-5 行足够。
- **当前假设**需要诚实：如果不确定原因是什么就说"不确定"。
- **卡住的根因**要具体，不是"代码有 bug"，而是"XXX 函数的类型签名与调用处的实际参数不匹配"。
- **需要人类帮助**必须是可以行动的问题，不是"帮我看看"——而是"帮我确认 XXX 参数应该是 string 还是 Buffer"。
- **下一步**可以写"暂无思路"——承认不知道比假装有下一步更好。

### Step 3 — 输出报告

打印完整的阻塞报告给用户。**不要添加额外评论、道歉或解释。** 模板是最小的刚好够用的格式。

- [ ] 所有 6 个章节都有实质性内容
- [ ] "需要人类帮助"的每一项都是可行动的
- [ ] 没有冗余段落或无关信息
