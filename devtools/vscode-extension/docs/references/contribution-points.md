<h2 id="contributes.commands" data-needslink="contributes.commands">contributes.commands</h2>
<p>Contribute the UI for a command consisting of a title and (optionally) an icon, category, and enabled state. Enablement is expressed with <a href="/api/references/when-clause-contexts">when clauses</a>. By default, commands show in the <strong>Command Palette</strong> (<span class="dynamic-keybinding" data-commandid="workbench.action.showCommands" data-osx="⇧⌘P" data-win="Ctrl+Shift+P" data-linux="Ctrl+Shift+P"><span class="keybinding">⇧⌘P</span> (Windows, Linux <span class="keybinding">Ctrl+Shift+P</span>)</span>) but they can also show in other <a href="/api/references/contribution-points#contributes.menus">menus</a>.</p>
<p>Presentation of contributed commands depends on the containing menu. The <strong>Command Palette</strong>, for
instance, prefixes commands with their <code>category</code>, allowing for easy grouping. However, the
<strong>Command Palette</strong> doesn't show icons nor disabled commands. The editor context menu, on the other
hand, shows disabled items but doesn't show the category label.</p>
<blockquote><p><strong>Note:</strong> When a command is invoked (from a key binding, from the <strong>Command Palette</strong>, any other menu, or programmatically), VS Code will emit an activationEvent <code>onCommand:${command}</code>.</p>
</blockquote><blockquote><p><strong>Note:</strong> When using icons from <a href="/api/references/icons-in-labels#icon-listing">product icons</a>, setting <code>light</code> and <code>dark</code> will disable the icon.

<h3 id="Configuration-schema" data-needslink="Configuration-schema">Configuration schema</h3>
<p>Your configuration entry is used both to provide intellisense when editing your settings in the JSON editor, and to define the way they appear in the settings UI.</p>
<p><img src="/assets/api/references/contribution-points/settings-ui.png" alt="settings UI screenshot with numbers" loading="lazy"></p>
<h4>title</h4>
<p>The <code>title</code> 1️⃣️ of a category is the heading used for that category.</p>
<pre class="shiki" data-lang="json" shiki-themes dark-plus light-plus" style="--shiki-dark:#D4D4D4;--shiki-light:#000000;--shiki-dark-bg:#1E1E1E;--shiki-light-bg:#FFFFFF" tabindex="0"><code><span class="line"><span style="--shiki-dark:#D4D4D4;--shiki-light:#000000">{</span></span>

<span class="line"><span style="--shiki-dark:#9CDCFE;--shiki-light:#0451A5">    "title"</span><span style="--shiki-dark:#D4D4D4;--shiki-light:#000000">: </span><span style="--shiki-dark:#CE9178;--shiki-light:#A31515">"GitMagic"</span></span>
<span class="line"><span style="--shiki-dark:#D4D4D4;--shiki-light:#000000">  }</span></span>
<span class="line"><span style="--shiki-dark:#D4D4D4;--shiki-light:#000000">}</span></span>
<span class="line"></span></code></pre>
<p>For an extension with multiple categories of settings, if the title of one of the categories is the same as the extension's display name, then the settings UI will treat that category as a "default category", ignoring the <code>order</code> field for that category and placing its settings below the main extension heading.</p>
<p>For both the <code>title</code> and <code>displayName</code> fields, words like "Extension", "Configuration", and "Settings" are redundant.</p>
<ul><li>✔ <code>"title": "GitMagic"</code></li>
<li>❌ <code>"title": "GitMagic Extension"</code></li>
<li>❌ <code>"title": "GitMagic Configuration"</code></li>
<li>❌ <code>"title": "GitMagic Extension Configuration Settings"</code></li>
</ul><h4>properties</h4>
<p>The <code>properties</code> 2️⃣ in your <code>configuration</code> object will form a dictionary where the keys are setting IDs and the values give more information on the setting. Though an extension can contain multiple categories of settings, each setting of the extension must still have its own unique ID. A setting ID cannot be a complete prefix of another setting ID.</p>
<p>Properties without an explicit <code>order</code> field will appear in lexicographical order in the settings UI (<strong>not</strong> the order in which they're listed in the manifest).</p>
<h3 id="Setting-titles" data-needslink="Setting-titles">Setting titles</h3>
<p>In the settings UI, multiple fields will be used to construct a display title for each setting. Capital letters in your key are used to indicate word breaks.</p>
<h4>Display titles for single-category and default category configurations</h4>
<p>If the configuration has a single category of settings, or if the category has the same title as the extension's display name, then for settings within that category, the settings UI will use the settings ID and the extension <code>name</code> field to determine the display title.</p>
<p>As an example, for settings ID <code>gitMagic.blame.dateFormat</code> and extension name <code>authorName.gitMagic</code>, because the prefix of the settings ID matches with the suffix of the extension name, the <code>gitMagic</code> part of the settings ID will be removed in the display title: "Blame: <strong>Date Format</strong>".</p>
<h4>Display titles for multi-category configurations</h4>
<p>If the configuration has multiple categories of settings, and the category does not have the same title as the extension's display name, then for settings within that category, the settings UI will use the settings ID and the category <code>id</code> field to determine the display title.</p>
<p>As an example, for settings ID <code>css.completion.completePropertyWithSemicolon</code> and category ID <code>css</code>, because the prefix of the settings ID matches with the suffix of the category ID, the <code>css</code> part of the settings ID will be removed in the settings UI, and the generated title for the setting will be "Completion: <strong>Complete Property With Semicolon</strong>".</p>

Schema</a>.</p>

<p>If an <code>object</code> or <code>array</code> type setting can also contain other types like nested objects, arrays, or null, then the value won't be rendered in the settings UI and can only be modified by editing the JSON directly. <h4>order</h4>
<p>Both categories and the settings within those categories can take an integer <code>order</code> type property, which gives a reference to how they should be sorted relative to other categories and/or settings.</p>
<p>If two categories have <code>order</code> properties, the category with the lower order number comes first. If a category is not given an <code>order</code> property, it appears after categories that were given that property.</p>
<p>If two settings within the same category have <code>order</code> properties, the setting with the lower order number comes first. If another setting within that same category is not given an <code>order</code> property, it will appear after settings in that category that were given that property.</p>
<p>If two categories have the same <code>order</code> property value, or if two settings within the same category have the same <code>order</code> property value, then they will be sorted in increasing lexicographical order within the settings UI.</p>
<h4>enum / enumDescriptions / markdownEnumDescriptions / enumItemLabels</h4>
<p>If you provide an array of items under the <code>enum</code> 7️⃣ property, the settings UI will render a dropdown menu of those items.</p>
<p>You can also provide an <code>enumDescriptions</code> property, an array of strings of the same length as the <code>enum</code> property. The <code>enumDescriptions</code> property provides a description in the settings UI at the bottom of the dropdown menu corresponding to each <code>enum</code> item. <br>
You can also use <code>markdownEnumDescriptions</code> instead of <code>enumDescriptions</code>, and your descriptions will be parsed as Markdown. <code>markdownEnumDescriptions</code> takes precedence over <code>enumDescriptions</code>. <br>
To customize the dropdown option names in the settings UI, you can use <code>enumItemLabels</code>.</p>

<h4>Other JSON Schema properties</h4>
<p>You can use any of the validation JSON Schema properties to describe other constraints on configuration values:</p>
<ul><li><code>default</code> for defining the default value of a property</li>
<li><code>minimum</code> and <code>maximum</code> for restricting numeric values</li>
<li><code>maxLength</code>, <code>minLength</code> for restricting string length</li>
<li><code>pattern</code> for restricting strings to a given regular expression</li>
<li><code>patternErrorMessage</code> for giving a tailored error message when a pattern does not match.</li>
<li><code>format</code> for restricting strings to well-known formats, such as <code>date</code>, <code>time</code>, <code>ipv4</code>, <code>email</code>,
and <code>uri</code></li>
<li><code>maxItems</code>, <code>minItems</code> for restricting array length</li>
<li><code>editPresentation</code> for controlling whether a single-line inputbox or multi-line textarea is rendered for the string setting in the Settings editor</li>
</ul><h4>Unsupported JSON Schema properties</h4>
<p>Not supported in the configuration section are:</p>
<ul><li><code>$ref</code> and <code>definition</code>: The configuration schemas needs to be self-contained and cannot make assumptions how the aggregated settings JSON schema document looks like.</li>
</ul><p>For more details on these and other features, see the <a href="https://json-schema.org/overview/what-is-jsonschema" class="external-link" target="_blank">JSON Schema Reference</a>.</p>
<h4>scope</h4>
<p>A configuration setting can have one of the following possible scopes:</p>
<ul><li><code>application</code> - Settings that apply to all instances of VS Code and can only be configured in user settings.</li>
<li><code>machine</code> - Machine specific settings that can be set only in user settings or only in remote settings. For example, an installation path which shouldn't be shared across machines. The value of these settings will not be synchronized.</li>
<li><code>machine-overridable</code> - Machine specific settings that can be overridden by workspace or folder settings. The value of these settings will not be synchronized.</li>
<li><code>window</code> - Windows (instance) specific settings which can be configured in user, workspace, or remote settings.</li>
<li><code>resource</code> - Resource settings, which apply to files and folders, and can be configured in all settings levels, even folder settings.</li>
<li><code>language-overridable</code> - Resource settings that can be overridable at a language level.</li>
</ul><p>Configuration scopes determine when a setting is available to the user through the Settings editor and whether the setting is applicable. If no <code>scope</code> is declared, the default is <code>window</code>.</p>

<p><code>customEditors</code> is an array, so your extension can contribute multiple custom editors.</p>
<ul><li>
<p><code>viewType</code> - Unique identifier for your custom editor.</p>
<p>This is how VS Code ties a custom editor contribution in the <code>package.json</code> to your custom editor implementation in code. This must be unique across all extensions, so instead of a generic <code>viewType</code> such as <code>"preview"</code> make sure to use one that is unique to your extension, for example <code>"viewType": "myAmazingExtension.svgPreview"</code>.</p>
</li>
<li>
<p><code>displayName</code> - Name that identifies the custom editor in VS Code's UI.</p>
<p>The display name is shown to the user in VS Code UI such as the <strong>View: Reopen with</strong> dropdown.</p>
</li>
<li>
<p><code>selector</code> - Specifies which files a custom editor is active for.</p>
<p>The <code>selector</code> is an array of one or more <a href="/docs/editor/glob-patterns">glob patterns</a>. These glob patterns are matched against file names to determine if the custom editor can be used for them. A <code>filenamePattern</code> such as <code>*.png</code> will enable the custom editor for all PNG files.</p>
<p>You can also create more specific patterns that match on file or directory names, for example <code>**/translations/*.json</code>.</p>
</li>
<li>
<p><code>priority</code> - (optional) Specifies when the custom editor is used.</p>
<p><code>priority</code> controls when a custom editor is used when a resource is open. Possible values are:</p>
<ul><li><code>"default"</code> - Try to use the custom editor for every file that matches the custom editor's <code>selector</code>. If there are multiple custom editors for a given file, the user will have to select which custom editor they want to use.</li>
<li><code>"option"</code> - Do not use the custom editor by default but allow users to switch to it or configure it as their default.</li>
</ul></li>
</ul><p>You can learn more in the <a href="/api/extension-guides/custom-editors">Custom Editors</a> extension guide.</p>
<h2 id="contributes.debuggers" data-needslink="contributes.debuggers">contributes.debuggers</h2>
<p>Contribute a debugger to VS Code. A debugger contribution has the following properties:</p>
<ul><li><code>type</code> is a unique ID that is used to identify this debugger in a launch configuration.</li>
<li><code>label</code> is the user visible name of this debugger in the UI.</li>
<li><code>program</code> the path to the debug adapter that implements the VS Code debug protocol against the real debugger or runtime.</li>
<li><code>runtime</code> if the path to the debug adapter is not an executable but needs a runtime.</li>
<li><code>configurationAttributes</code> is the schema for launch configuration arguments specific to this debugger. Please note that the JSON schema constructs <code>$ref</code> and <code>definition</code> are not supported.</li>
<li><code>initialConfigurations</code> lists launch configurations that are used to populate an initial launch.json.</li>
<li><code>configurationSnippets</code> lists launch configurations that are available through IntelliSense when editing a launch.json.</li>
<li><code>variables</code> introduces substitution variables and binds them to commands implemented by the debugger extension.</li>
<li><code>languages</code> those languages for which the debug extension could be considered the "default debugger".</li>

<h2 id="contributes.menus" data-needslink="contributes.menus">contributes.menus</h2>
<p>Contribute a menu item for a command to the editor or Explorer. The menu item definition contains the command that should be invoked when selected and the condition under which the item should show. The latter is defined with the <code>when</code> clause, which uses the key bindings <a href="/api/references/when-clause-contexts">when clause contexts</a>.</p>
<p>A <code>command</code> property indicates which command to run when selecting a menu item. A <code>submenu</code> property indicates which submenu to render in this location.</p>
<p>When declaring a <code>command</code> menu item, an alternative command can also be defined using the <code>alt</code>-property. It will be shown and invoked when pressing <span class="keybinding">Alt</span> while opening a menu. On Windows and Linux <span class="keybinding">Shift</span> also does this, which is useful in situations where <span class="keybinding">Alt</span> would trigger the window menu bar.</p>
<p>Last, a <code>group</code> property defines sorting and grouping of menu items. The <code>navigation</code> group is special as it will always be sorted to the top/beginning of a menu.</p>
<blockquote><p><strong>Note</strong> that <code>when</code> clauses apply to menus and <code>enablement</code> clauses to commands. The <code>enablement</code> applies to all menus and even keybindings while the <code>when</code> only applies to a single menu.</p>
</blockquote><p>Currently extension writers can contribute to:</p>

<h3 id="Sorting-of-groups" data-needslink="Sorting-of-groups">Sorting of groups</h3>
<p>Menu items can be sorted into groups. They are sorted in lexicographical order with the following defaults/rules.
You can add menu items to these groups or add new groups of menu items in between, below, or above.</p>
<p>The <strong>editor context menu</strong> has these default groups:</p>
<ul><li><code>navigation</code> - The <code>navigation</code> group comes first in all cases.</li>
<li><code>1_modification</code> - This group comes next and contains commands that modify your code.</li>
<li><code>9_cutcopypaste</code> - The second last default group with the basic editing commands.</li>
<li><code>z_commands</code> - The last default group with an entry to open the Command Palette.</li>
</ul><p><img src="/assets/api/references/contribution-points/groupSorting.png" alt="Menu Group Sorting" loading="lazy"></p>

<ul><li><code>navigation</code> - Commands related to navigation across VS Code. This group comes first in all cases.</li>

<li><code>3_compare</code> - Commands related to comparing files in the diff editor.</li>

<p>The task definition is defined using JSON schema syntax for the <code>required</code> and <code>properties</code> property. The <code>type</code> property defines the task type. If the above example:</p>

<li><code>"properties" : { ... }</code> defines the additional properties and their types.</li>
</ul><p>When the extension actually creates a Task, it needs to pass a <code>TaskDefinition</code> that conforms to the task definition contributed in the package.json file. For the <code>npm</code> example a task creation for the test script inside a package.json file looks like this:</p>

<h2 id="contributes.views" data-needslink="contributes.views">contributes.views</h2>
<p>Contribute a view to VS Code. You must specify an identifier and name for the view. You can contribute to following view containers:</p>
<ul><li><code>explorer</code>: Explorer view container in the Activity Bar</li>
<li><code>scm</code>: Source Control Management (SCM) view container in the Activity Bar</li>
<li><code>debug</code>: Run and Debug view container in the Activity Bar</li>
<li><code>test</code>: Test view container in the Activity Bar</li>
<li><a href="#_contributes.viewsContainers">Custom view containers</a> contributed by Extensions.</li>
</ul><p>When the user opens the view, VS Code will then emit an activationEvent <code>onView:${viewId}</code> (<code>onView:nodeDependencies</code> for the example below). You can also control the visibility of the view by providing the <code>when</code> context value. The <code>icon</code> specified will be used when the title cannot be shown (e.g. when the view is dragged to the Activity Bar). The <code>contextualTitle</code> is used when the view is moved out of its default view container and needs additional context.</p>

<p>The content of a view can be populated in two ways:</p>
<ul><li>With a <a href="/api/references/vscode-api#TreeView">TreeView</a> by providing a <a href="/api/references/vscode-api#TreeDataProvider">data provider</a> through <code>createTreeView</code> API or register the <a href="/api/references/vscode-api#TreeDataProvider">data provider</a> directly through <code>registerTreeDataProvider</code> API to populate data. TreeViews are ideal for showing hierarchical data and lists. Webview views allow rendering arbitrary HTML in the view. See the <a href="https://github.com/microsoft/vscode-extension-samples/tree/main/webview-view-sample" class="external-link" target="_blank">webview view sample extension</a> for more details.</li>

<h2 id="contributes.walkthroughs" data-needslink="contributes.walkthroughs">contributes.walkthroughs</h2>
<p><a href="https://github.com/microsoft/vscode-extension-samples/tree/main/getting-started-sample" class="external-link" target="_blank">Sample extension</a></p>
<p>Contribute walkthroughs to appear on the Getting Started page. Walkthroughs are automatically opened on install of your extension and provide a convenient way to introduce users to features of your extension.</p>
<p>Walkthroughs consist of a title, description, id, and a series of steps. Additionally, a <code>when</code> condition can be set to hide or show the walkthrough based on context keys. For example, a walkthrough to explain setup on a Linux platform could be given <code>when: "isLinux"</code> to only appear on Linux machines.</p>
<p>Each step in a walkthrough has a title, description, id, and media element (either an image or Markdown content), along with an optional set of events that will cause the step to be checked (shown in the example below). Step descriptions are Markdown content, and support <code>**bold**</code>, <code>__underlined__</code>, and <code>``code``</code> rendering, as well as links. Similar to walkthroughs, steps can be given when conditions to hide or show them based on context keys.</p>
<p>SVGs are recommended for images given their ability to scale and their support for VS Code's theme colors. Use the <a href="https://www.figma.com/community/plugin/1218260433851630449" class="external-link" target="_blank">Visual Studio Code Color Mapper</a> Figma plugin to easily reference theme colors in the SVGs.</p>

<h3 id="Completion-events" data-needslink="Completion-events">Completion events</h3>
<p>By default, if no <code>completionEvents</code> events are provided, the step will be checked off when any of it's buttons are clicked, or if the step has no buttons, when it is opened. If finer control is required, a list of <code>completionEvents</code> can be provided.</p>
<p>Available completion events include:</p>
<ul><li><code>onCommand:myCommand.id</code>: Check off step when a command has been run.</li>
<li><code>onSettingChanged:mySetting.id</code>: Check off step once the given setting has been modified.</li>
<li><code>onContext:contextKeyExpression</code>: Check off step when a context key expression evaluates true.</li>
<li><code>extensionInstalled:myExt.id</code>: Check off step if the given extension is installed.</li>
<li><code>onView:myView.id</code>: Check off step once a given view becomes visible.</li>
<li><code>onLink:https://...</code>: Check off step once a given link has been opened via a Walkthrough.</li>
</ul><p>Once a step has been checked off, it will remain checked off until the user explicitly unchecks the step or resets their progress (via the <strong>Getting Started: Reset Progress</strong> command).</p>
