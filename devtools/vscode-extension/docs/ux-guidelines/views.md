			<main class="docs-main-content body"><h1>Views</h1>
<p><a href="/api/references/contribution-points#contributes.views">Views</a> are containers of content that can appear in the Sidebar or Panel. Views can contain Tree Views, Welcome Views, or Webview Views and can also display View Actions. Views can also be rearranged by the user or moved to another View Container (for example, from the Primary Sidebar to the Secondary Sidebar). Limit the number of Views created as other extensions can contribute in the same View Container.</p>
<p><strong>✔️ Do</strong></p>
<ul><li>Use existing icons when possible</li>
<li>Use file icons for language files</li>
<li>Use a Tree View for displaying data</li>
<li>Add an icon to every View (in case it is moved to the Activity Bar or Secondary Sidebar—both of which use icons to represent the View)</li>
<li>Keep the number of Views to a minimum</li>
<li>Keep the length of names to a minimum</li>
<li>Limit the use of custom Webview Views</li>
</ul><p><strong>❌ Don't</strong></p>
<ul><li>Repeat existing functionality</li>
<li>Use tree items as single action items (for example, firing a Command on click)</li>
<li>Use custom Webview Views if not necessary</li>
<li>Use a Activity Bar Item (View Container) to open a Webview in the Editor</li>
</ul><p><img src="/assets/api/ux-guidelines/examples/view.png" alt="Views example" loading="lazy"></p>
<p><em>This example uses a Tree View to display a flat list of Tree View Items.</em></p>
<h2 id="view-locations" data-needslink="view-locations">View Locations</h2>
<p>Views can be placed in <a href="/api/references/contribution-points#contributes.views">existing View Containers</a>, such as the File Explorer, Source Control (SCM) and Debug View Containers. They can also be added to a custom <a href="/api/ux-guidelines/views#view-containers">View Container</a> via the Activity Bar. In addition, Views can be added to any View Container in the Panel. They can also be dragged to the Secondary Sidebar.</p>
<p><img src="/assets/api/ux-guidelines/examples/view-locations.png" alt="View locations" loading="lazy"></p>
<h2 id="view-containers" data-needslink="view-containers">View Containers</h2>
<p>View Containers, as the name implies, are the "parent" container in which Views are rendered. Extensions can contribute custom View Containers to the <a href="/api/ux-guidelines/activity-bar">Activity Bar</a>/<a href="/api/ux-guidelines/sidebars">Primary Sidebar</a> or to the Panel. Users can drag an entire View Container from the Activity Bar to the Panel (or vice versa) and can also move individual Views.</p>
<p><img src="/assets/api/ux-guidelines/examples/view-container.png" alt="Example of a View Container" loading="lazy"></p>
<p><em>This is an example of a View Container placed in the Activity Bar/Primary Sidebar</em></p>
<p><img src="/assets/api/ux-guidelines/examples/view-container-panel.png" alt="Example of a View Container in a Panel" loading="lazy"></p>
<p><em>This is an example of a View Container placed in the Panel</em></p>
<h2 id="tree-views" data-needslink="tree-views">Tree Views</h2>
<p>Tree Views are a powerful and flexible format to display content in a View. Extensions can add everything from simple flat lists to deeply nested trees.</p>
<ul><li>Use descriptive labels to give context to items (if applicable)</li>
<li>Use product icons to distinguish between item types (if applicable)</li>
</ul><p><strong>❌ Don't</strong></p>
<ul><li>Use Tree View Items as buttons to fire Commands</li>
<li>Avoid deep nesting unless necessary. A few levels of folders/items is a good balance for most situations.</li>
<li>Add more than three actions to an item</li>
</ul><p><img src="/assets/api/ux-guidelines/examples/tree-view.png" alt="Example of a Tree View" loading="lazy"></p>
<h2 id="welcome-views" data-needslink="welcome-views">Welcome Views</h2>
<p>When a view is empty, you can <a href="/api/references/contribution-points#contributes.viewsWelcome">add content to guide users</a> on how to use your extension or get started. Links and icons are supported in Welcome views.</p>
<p><strong>✔️ Do</strong></p>
<ul><li>Use Welcome views only when necessary</li>
<li>Use links instead of buttons when possible</li>
<li>Use buttons only for primary actions</li>
<li>Use clear link text to indicate the link destination</li>
<li>Limit the length of the content</li>
<li>Limit the number of Welcome views</li>
<li>Limit the number of buttons in views</li>
</ul><p><strong>❌ Don't</strong></p>
<ul><li>Use buttons if not necessary</li>
<li>Use Welcome views for promotions</li>
<li>Use generic "read more" as link text</li>
</ul><p><img src="/assets/api/ux-guidelines/examples/welcome-view.png" alt="Welcome Views" loading="lazy"></p>
<p><em>This example shows one primary action for the extension with an additional link to documentation.</em></p>
<h2 id="views-with-progress" data-needslink="views-with-progress">Views With Progress</h2>
<p>You can also <a href="/api/references/vscode-api#ProgressLocation">show progress in a view</a> by referencing the view's ID.</p>
<p><img src="/assets/api/ux-guidelines/examples/view-with-progress.png" alt="View with progress" loading="lazy"></p>
<h2 id="view-actions" data-needslink="view-actions">View Actions</h2>
<p>Views can expose <a href="/api/extension-guides/tree-view#view-actions">View Actions</a> on the View Toolbar. Be careful not to add too many actions to avoid noise and confusion. Using the built-in product icons helps an extension fit in alongside the native UI. However, an SVG icon can be supplied if a custom icon is needed.</p>
<p><img src="/assets/api/ux-guidelines/examples/view-toolbar.png" alt="Example of View Actions" loading="lazy"></p>
