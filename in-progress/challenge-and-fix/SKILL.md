# challenge-and-fix — 每条意见一个对抗员，主 session 统一修

## 卡位

| Skill | 单位 | 问题 |
|---|---|---|
| **fix** | 一条意见 | 主 session 亲自 verify + fix（串行） |
| **challenge-audit** | 整份报告 | 这位评审还值得信吗 |
| **challenge-and-fix** | 一条意见 × 一个 subagent | 意见成立吗？方案最优吗？并行定谳 |

意见多、或想并行处理时用本 skill；主 session 只做派发、综合、修复三件事，对抗外包，修复不外包。链路：报告可信度存疑先走 `challenge-audit`，本 skill 定谳后，修复执行与回归验证按 `fix` 的方法域走。

## 主 session 流程

1. **编号意见**：把评审产出的每条意见逐字列出（不转述、不合并），编为 F1..Fn。
2. **逐条派发**：每条意见一个 subagent（agent 名用 `challenger`，只读角色），prompt 按下方注入模板写，context 用 fresh。
3. **综合定谳**：收齐 n 份裁决——REJECT 丢弃该意见（落修复前抽查其反证，对抗员的结论也是 claim）；ACCEPT 沿用原推荐方案；PROPOSE 采用新方案。
4. **亲自修复**：主 session 自己完成所有修复。subagent 全程只读，不改任何文件。

**完成判据**：n 条意见 → n 份裁决，每份含裁决值 + 依据；修复清单 = ACCEPT 方案 ∪ PROPOSE 方案，REJECT 全部有反证可查。

## 注入模板

首行 skill 名后紧跟一个空格再写角色词，再换行写正文（换行/双换行分隔在注入路径上不可靠）：

```
/skill:challenge-and-fix 单条意见对抗员

## 指派意见
<意见原文逐字>

## 定位
<仓库路径 / 文件 / commit 或 MR / 相关 diff 范围>

## 输出
按 SKILL.md 输出格式返回一份裁决。你是只读角色，不修改任何文件。
```

## 对抗员流程（subagent 侧）

**只接一条意见**，一轮跑完三步：

1. **取证**：读定位范围内的代码 / diff，确认意见声称的问题在真实代码里长什么样。
2. **对抗三问**（按序问，命中即停）：
   - **引用失真？** 意见描述的代码行为与实际不符（行号错、语义读反、断章取义）→ REJECT 候选。
   - **依据不成立？** 意见引用的规则 / 前提在本仓不适用——fork 特例、既有项目约定、上游刻意设计（先读注释再定性）→ REJECT 候选。
   - **方案次优？** 问题成立，但推荐修复有更简 / 更对 / 更不破坏现状的替代 → PROPOSE 候选。三问都未命中 → ACCEPT。
3. **定谳三选一**，按输出格式返回。

**驳回要反证**：REJECT 必须给出正面反证（file:line 引用，或可复跑的验证命令及结果）。"没找到问题"、"我没复现"不算反证——证据不足时意见按成立处理，在 ACCEPT / PROPOSE 里选。

## 输出格式

```
## 裁决: REJECT | ACCEPT | PROPOSE
- 意见核实: <成立 / 不成立 + 依据 file:line>
- 证据: <引用失真 / 依据不成立 / 方案对比的具体证据>
- 修复方案: <ACCEPT 引用原方案；PROPOSE 给新方案（落点、改法、为何优于原方案、验证方式）；REJECT 写"无">
```

## 工作规则

- **只读红线**：对抗员不编辑任何文件；修复是主 session 的职责，任何一方不得代写。
- **一条一个 agent**：意见之间不共享上下文，避免连锁翻案和串联口径。
- **parent 核实后再落**：主 session 采纳 PROPOSE 前按自己的判断复核新方案；REJECT 的反证至少抽查一条。
