# Replay Compare

Selecting between two interchangeable backends (search engines, extractors,
routers)? Vendor benchmarks are self-serving and generic. Your own session
history is the honest workload. This skill replays it.

## Pipeline

```text
tool-call-extract (triage) → extract-queries.py → sample-queries.py
→ replay runner (per-comparison script) → stats + eyeball → report
```

### Step 1: Extract historical queries

Find the sessions that invoked the incumbent tool. For triage/stats use the
`tool-call-extract` skill (`find-tool-calls.py bash --args-contains <cli-name>`).
For the actual query corpus use the bundled extractor, which walks **all**
session JSONLs and pulls query strings out of toolCall commands:

```bash
python3 <SKILL_DIR>/scripts/extract-queries.py \
  --match "anysearch_cli" \
  --regex '\bsearch\s+"([^"]+)"' \
  --regex '--query\s+"([^"]+)"' \
  > queries.txt
```

- `--match` filters JSONL lines containing this substring (CLI/script name of
  the tool). `--regex` (repeatable) captures the query with group 1. Defaults
  are tuned for the anysearch CLI; override for other tools.
- Built-in junk filter drops test invocations (`q1`, `query2`, `\`, `test*`,
  len < 8). Inspect the head of the output anyway — leaked test queries
  poison the sample.
- Drop queries generated by the *current* comparison session itself, or you
  will measure the tool searching for its own evaluation.

Done when: `queries.txt` has a frequency-sorted corpus and its size is stated.

### Step 2: Stratified sample

Do not replay everything (cost + time). Bucket by theme, sample proportional
to bucket size, prefer frequently-asked queries, dedupe near-duplicates:

```bash
python3 <SKILL_DIR>/scripts/sample-queries.py \
  --in queries.txt --out sample.json --target 30 --seed 42
```

- Default buckets (LLM-inference / agent-arch / data-pipeline / cost-finance
  / infra-tools / other) fit a coding-agent research workload; pass
  `--buckets buckets.json` (`[["name", "regex"], ...]`) to match the corpus.
- Record bucket sizes in the report — the sample must be reproducible
  (`--seed`, keep `sample.json` in the workspace).

### Step 3: Build the replay runner

Copy `scripts/replay-runner.template.mts` and write one leg function per
backend. Rules the template encodes — do not skip them:

- **One JSON file per (query, leg)** under `results/`, resumable: existing
  files are skipped, so crashes and staged legs (e.g. waiting for an API key)
  are free.
- **Node fetch ignores proxy env.** On corporate networks set
  `NODE_USE_ENV_PROXY=1` when running, or every fetch-based leg fails in <1s
  with `fetch failed` while curl works. This cost a debugging round-trip once
  already.
- Import the competitor's own code path where possible (e.g. call the
  extension's exported `performSearch`, not a re-implementation) so the
  measurement is faithful.
- Politeness delay between queries (default 1.2s); replay-only modes (no LLM
  in the loop) still hammer real endpoints.
- Record per-leg: raw payload, latency ms, provider, error string. Never
  truncate raw payloads — the eyeball step and the report citations need them.

### Step 4: Run

Under ~5 min: foreground. Longer: `bg_run`, do not poll.

### Step 5: Stats + quality eyeball

Mechanical stats in one pass (成功率 / 结果数 / latency avg+p50 per leg).
Then manually compare 4-6 representative queries across legs (one docs
lookup, one concept, one niche paper, one entity lookup) and print the top
results side by side. Quality judgement stays human-in-the-loop here; a
full relevance judgment is out of scope.

### Step 6: Report

Lay out `~/research/<topic-slug>/` per the `research` skill: one direction
report per backend, `00-summary.md` synthesizes with the replay table. Cite
raw result files (`~/tmp/<workspace>/results/`) as evidence.

## Workspace convention

Everything lands in `~/tmp/<compare-slug>/`: `queries.txt`, `sample.json`,
`replay.mts`, `results/`. Raw data is cheap; regenerate reports from it.
Remind the user afterwards that the extraction→replay flow is now this skill.
