# Debug methods — 调试心法（事实层/推导层约束满足）

> 来源：Cindy Sridharan《How to effectively debug when you no longer understand the code》（白明转述版：mp.weixin.qq.com/s/SB13MWXxz-a9ymn_-us5-g）。精读与 ops 落地映射：~/research/ara-vs-knowledge-systems/06-rca-debug-methods.md。
> 本文件是 SKILL.md 各 phase 引用的方法论深读，只读不改流程。

## 两层框架

调试 = 约束满足问题。所有材料分两层：

- **事实层**：日志、抓包、profile、配置、内核数据、指标序列——工具采集的客观数据，agent 只观察，不篡改。
- **推导层**：假设、推论、叙事——agent 最擅长讲故事，也最容易错。

规则：事实层每条事实都是**约束**；候选假设只要与任一条事实矛盾，即丢弃。幸存假设 = 满足全部约束。

**代码属于推导层的输入，不是事实层。**

## 三步循环（Phase 3/4 的排序与裁决依据）

1. **对照找信号**：只出现在变量、不出现在对照组的数据才是高保真信号；两边都有的只用于排除假设。对照路径差异太大时，选一个"失败得更响亮"的案例做对照。
2. **找强信号**：能被多个假设同时解释的是弱信号（SLO/SLI 类聚合指标往往只是症状），只有一两个假设能解释的才是强信号。排序工具：**假设 × 事实矩阵**——行是假设，列是关键事实，格填 ✓/✗/无数据；只有一列只有一个 ✓，那一列就是定因信号。
3. **全量验证**：幸存假设必须经受事实层**每一条**事实的检验（包括噪声）；矛盾一条即弃。

## 与各 phase 的接口

- **Phase 0（vault）**：命中笔记的"排除的假设"清单 = 本轮约束的先验来源；命中笔记的复现可信度标注决定其证据权重。
- **Phase 2（复现）**：复现属于推导层。**复现要打折扣**——只有当复现产出与真实案例相同的强信号时才可信；抓包/状态后半段与真实案例不同的"复现"是另一个 bug（原文真实案例：时钟偏差令牌复现，症状一致但内核 IPC 表缺关键票据）。diag-write 写入时须标注复现可信度。
- **Phase 3（假设）**：3-5 个假设生成后，用假设 × 事实矩阵排序（上表），强信号优先验证；禁止被 SLO 类弱信号锚定。
- **Phase 4（取证）**：信号都弱就**下潜一层**采更底层数据（渐进式信号发现），出现强信号即停——目标是"最强"不是"最深"。人类下潜一两层就放弃，agent 不知疲倦，这是它的优势。
- **Phase 5（修复）**：对抗式评审是**排除器不是验证器**——让它找反例做排除，每条结论必须附证据引用；给不出引用的结论按未验证处理。

## 反模式清单

- **先读代码是反模式**：代码只告诉你"可能发生什么"，不是"实际发生了什么"。agent 会自己挑代码片段，从看似合理的角度一路走偏。读代码是调查的最后一步（Phase 1 的 feedback loop 优先级不变，本条是它的理论支撑）。
- **对抗式评审当验证器**：同一模型同上下文的评审者容易"一个观点算两遍"。
- **复现即真相**：见上，复现必须通过强信号对齐才算数。
- **本地盒子当生产**：本地环境无法还原生产的事实层。生产问题应以只读、限时、可审计方式直接访问生产信号。

## 结论引用纪律

每条机制性结论必须带证据锚点（命令输出 / 指标序列 / session-id#entry / 文件:行号）。给不出引用的结论 = 未验证的假设，不得进入 Phase 5/6 的 commit 理由与 vault 根因字段。
