An HTML presentation has arrived — generated by impeccable or a peer session, soon to be shared with a technical audience. Style has been reviewed, rendering verified. What nobody checked: **will the audience understand it?** Concepts the author lives with for weeks are strangers to the reader; data that begs a chart sits in a paragraph; the same thing gets three names. This skill puts one reviewer on each comprehension axis and reports what will trip the reader.

**Scope boundary — comprehensibility, not correctness.** Whether a claim is true is out of scope (no ground-truth cross-check). Whether the audience can follow it is the whole job.

## Position in the check stack

| Layer | Skill | Asks |
|-------|-------|------|
| Style / visual design | impeccable | does it look good? |
| Structure + render | html-render-check | does it parse and render clean? |
| **Comprehension** | **this skill** | **can the audience follow it?** |

Runtime requirements are identical to html-render-check (Playwright under `~/tools/playwright-runner`, `--no-sandbox` on cluster nodes). On a fresh node, set up html-render-check first; this skill rides the same runtime. Screenshot capture reuses that stack via this skill's `scripts/section-shots.mjs`.

## Process

1. **Locate and read the artifact.** Read the HTML fully. Note its section structure, the domain it covers, and the concepts it introduces. Check for a `CONTEXT.md` in the project directory — if present, it becomes the canonical vocabulary for Check 5.

2. **Pin the audience.** From the content, guess who this is for, then ask the user via `ask_user_question` with 2–4 concrete audience options (e.g. "backend engineers who know GPU basics but not CXL" / "infra team familiar with the project" / "mixed technical audience, no domain background"). The confirmed audience is quoted verbatim into every check brief — every axis judges against it.

3. **Capture screenshots.** Run `node <SKILL_DIR>/scripts/section-shots.mjs --out-dir <tmpdir> <file.html>`. This emits one fullPage shot plus one shot per `<section>`/`<article>` element, with a `manifest.json` mapping each shot to its heading.

4. **Probe the vision model.** Call `subagent({ action: "models" })` and look for a vision-capable model (id containing `vision`, `4v`, `-v` style multimodal names). If found, Checks 2 and 3 run their subagents with that exact `provider/id` as the `model` override. If none exists, Checks 2 and 3 fall back to DOM-level analysis (see each check).

5. **Verify the review agent, then spawn six sub-agents in parallel.** Before spawning:
   - Load the `pi-subagents` skill once (read its SKILL.md and `references/execution-controls.md`) — it holds the verified `runs.run`/`runs.all` signatures. Do not write the dispatch script from memory.
   - Run `subagent({ action: "list" })` to confirm `doc-reviewer` is registered, and check its config (`~/.pi/agent/agents/doc-reviewer.md`) has `acceptance: false` and read-only tools.

   Each sub-agent gets: the HTML path, the **audience quote**, the screenshot dir + manifest path (vision axes), the `CONTEXT.md` path if found (Check 5), and the check's body as its brief. Use `runs.all` with `context: 'fresh'`. Pass every path explicitly — fresh-context children see only what the brief carries. Per repo convention, each sub-agent writes its findings to a file **and** returns them via stdout.

6. **Aggregate and report.** Combine the six reports under six headings. Keep findings per-axis (no dedup across axes — overlaps are signal, not noise). Present the report; do not fix, do not route, do not re-inspect. Re-review happens when the user manually invokes this skill again after revisions.

## The six checks

Each check's body is the sub-agent's brief. Each sub-agent reports under 400 words, one finding per item.

### 1 — Concept reachability

Every concept the audience doesn't already hold must be explained **where it first matters**. Scan the document for domain terms, acronyms, and coined names (product/feature names like "CXL L2 Index Server"). For each: locate its first occurrence; check whether an explanation suitable for the quoted audience appears inline there or earlier — not three sections later, not only in a glossary the reader hasn't been pointed at. Acronyms must be expanded on first use unless ubiquitous for the audience (CPU, API yes; DPDK, ITL depends — judge against the audience quote).

**Done when**: an inventory of every new concept exists, each marked defined-at-first-use / defined-later / never-defined, with location.

### 2 — Visualization coverage

Complex data and processes must be visualized, not narrated. Find passages that make the reader construct a mental picture: multi-series comparisons, trends over a sequence, distributions, step-by-step flows with branches, spatial/topological relationships. For each, check the corresponding screenshot: is there a chart/diagram, or is a paragraph or dense table doing the work a picture should?

**Vision available**: judge from section screenshots — read each section's prose against its visual. **DOM fallback**: inspect the HTML source — flag data-dense prose passages with no sibling `svg`/`canvas`/`figure`/`img`, and mark every finding "advisory — not render-verified".

**Done when**: every complex-data/complex-flow passage is listed as has-visual / needs-visual, with location.

### 3 — Chart self-explanation

Every chart must stand alone. For each chart in the screenshots: are axis labels/units/legend present where applicable? Is there a caption or title stating what it shows? Does the surrounding prose reference the chart ("see Fig. X" or equivalent) and does the chart's story match what the prose claims? A chart the reader must reverse-engineer is a finding. Also flag decorative charts — visuals that carry no information the prose depends on.

**DOM fallback**: check the markup for axis/legend text elements, `<figcaption>`/`<title>`, and prose references; mark "advisory — not render-verified".

**Done when**: every chart is assessed on labeled / captioned / referenced / matches-prose, with location.

### 4 — Prerequisite ordering

The document must be readable front-to-back on first pass. Walk it in order: does any section use a concept, mechanism, or result that is only explained in a later section — without a forward pointer ("explained in §07")? Does the argument build, or does the reader need to hold unexplained things in mind? Judge strictly against the audience quote: what counts as "already known" is what the audience brings, not what the author does.

**Done when**: every forward-reference is either preceded by an explanation or flagged, with both locations.

### 5 — Terminology consistency

One concept, one name. Collect every named concept and its variants (synonyms, abbreviations, English/Chinese pairs like "L2 索引服务" vs "index server"). Flag cases where two names are used interchangeably without the document ever stating they are the same — the reader cannot tell synonym from distinction. If a `CONTEXT.md` exists, it is the canonical vocabulary: name-spellings that contradict it are findings.

**Done when**: a term→variants table exists, and every interchangeably-used variant pair without an explicit "same thing" statement is flagged.

### 6 — Takeaway visibility

Every section must yield its point at a glance. For each section: can the reader extract the conclusion in ~10 seconds — a bolded takeaway, a summary line, a callout — or is the point buried mid-paragraph in prose? Is there an executive summary / overview the time-poor reader can stop at? A section whose point requires reading every sentence to find is a finding.

**Done when**: every section is marked has-takeaway / buried, plus an overall summary-presence verdict.

## Report

Present the six check reports under six headings (`## 1 — Concept reachability`, etc.), lightly cleaned from the sub-agent outputs. Then a summary table, **high before low**:

| # | Check | Severity | Location | Finding (short) |
|---|-------|----------|----------|-----------------|

**Severity**: `high` = the audience will fail to understand something central (undefined concept the argument depends on, complex data with no visual, contradictory terminology, takeaway absent for a key section). `low` = friction, suboptimal but survivable (defined later with a pointer, chart missing a caption, low-stakes term drift).

End with a one-line verdict: "N high, M low across K axes" and where the report file was written. Write the aggregated report to `<html-dir>/<name>.clarity-review.md` and show the summary on stdout.

**Report only.** No fixes, no routing, no automatic re-inspect — the user decides what to do with the findings and may re-invoke this skill after revisions.
