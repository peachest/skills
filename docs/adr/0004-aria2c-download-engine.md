# Bilibili audio download uses aria2c subprocess, not requests.stream

The `fetch-article` bilibili adapter downloads audio via `subprocess` invocation of aria2c (a standalone download manager), not via `requests.stream` chunked download. This was chosen to get native cross-call resumption (aria2c's `.aria2` control file survives process restarts), built-in Content-Length verification (aria2c exits non-zero on incomplete downloads), and reliable proxy support (`--all-proxy` reads the URL directly, avoiding the aiohttp/requests env-reading ambiguity that caused DNS failures in the original sessions). The trade-off is a binary dependency: aria2c must be present in PATH or at `~/scripts/aria2c`.

**Considered alternatives**: Keep `requests.stream` and implement a custom sidecar `.partial.meta` file for cross-call resumption (rejected — reimplements what aria2c already does, and `requests`' env-proxy behavior was part of the original failure). Single-call-only resume via HTTP Range within one `fetch()` invocation, no cross-call persistence (rejected — user explicitly wanted cross-process resumption for long videos interrupted by timeouts).

**Consequences**: The adapter's download layer is now a subprocess call, which tests must mock at the `subprocess.run` level (not HTTP). The deterministic workspace `~/.cache/fetch-bilibili/<bvid>/` replaces random `tempfile.mkdtemp` so the `.aria2` control file is findable on re-run. WBI signing and all Bilibili API calls (nav/view/player.v2/playurl) remain on `requests.Session` — only the CDN audio download uses aria2c.
